# Conditional physical optimization notes

This note is a path-driven decision aid for later Series 7 implementation runs. The current native profile and constraints remain frozen; this note does not authorize a run or change them. Vivado 2026.1 documentation was checked on 2026-11-08. The workspace already accepted the `AggressiveFanoutOpt` directive in an earlier route, so command recognition is established locally; its benefit on the new adaptive candidate is not.

## Decide from the routed path

Use the next actual route report to separate cell delay from net delay, then inspect the critical driver’s fanout and placement spread, the logic depth, and any DSP endpoints. Keep the next experiment tied to the observed bottleneck.

| New path evidence | Conditional next step | What this option cannot establish |
| --- | --- | --- |
| A critical high-fanout driver has substantial net delay and enough negative slack for optimization | Compare the already-supported pre-route `phys_opt_design -directive AggressiveFanoutOpt` against the current default. AMD describes this directive as using more aggressive fanout algorithms; physical optimization can replicate high-fanout timing-critical drivers. Review the resulting replicas, WNS/TNS, utilization, and routing. [UG835: `phys_opt_design`](https://docs.amd.com/r/en-US/ug835-vivado-tcl-commands/phys_opt_design) | A better result is not guaranteed. More replicas can consume resources and worsen placement or congestion. This is not a general fix for logic depth or a low-fanout long route. |
| The critical net has low fanout but long route delay | Treat placement/locality or congestion as the issue; fanout replication is not evidence-based for this path. Record the exact driver/sink and net-versus-cell delay before choosing another implementation hypothesis. | Do not infer that more fanout optimization will shorten a low-fanout route. The current experiment set does not authorize new placement constraints or directives. |
| Cell delay or many LUT levels dominate before the route | Inspect synthesized logic and mapping first. AMD documents `RuntimeOptimized` as doing fewer timing optimizations and omitting some RTL optimizations for faster synthesis; `Default` is the default strategy. A later, separately authorized comparison with `Default` is reasonable only if synthesis evidence links the path to those omitted optimizations. [UG901: synthesis settings](https://docs.amd.com/r/en-US/ug901-vivado-synthesis/Using-Synthesis-Settings), [UG901: preconfigured strategies](https://docs.amd.com/r/en-US/ug901-vivado-synthesis/Vivado-Preconfigured-Strategies) | Changing the synthesis strategy does not repair a route-dominated path by itself. The current adaptive profile is frozen at `RuntimeOptimized`; do not change it during the active experiment. |
| A sequential path through a LUT cone is critical and legal register movement could shorten it | Consider retiming only as a later, controlled hypothesis. UG901 describes global retiming as moving registers across combinational gates/LUTs while preserving circuit behavior and latency. It is a design-wide setting unless scoped using supported attributes or constraints. On non-Versal devices, `global_retiming=Auto` does not perform retiming; in OOC mode, registers at module ports are not retimed. [UG901: synthesis settings](https://docs.amd.com/r/en-US/ug901-vivado-synthesis/Using-Synthesis-Settings), [UG901: synthesis scope](https://docs.amd.com/r/en-US/ug901-vivado-synthesis/Overview) | Retiming is not a substitute for identifying the path endpoints, and no latency/cycle equivalence should be inferred without the existing exact-cycle canonical gate. No retiming option is added to the current frozen profile. |
| A critical DSP-input path appears register-limited | Read the mapped DSP primitive and path endpoints. The documented DSP-register optimization can pull an adjacent fabric FF into AREG/BREG when timing to the DSP input is critical; it can also push AREG/BREG stages into fabric when timing into the DSP register is critical but timing out is comfortable. These are conditional on actual slack, not aggregate register counts. [UG904: DSP register optimization](https://docs.amd.com/r/en-US/ug904-vivado-implementation/DSP-Register-Opt) | `USE_DSP` controls arithmetic-to-DSP inference; it does not promise a particular AREG/BREG stage mapping. Register configuration must be read from the mapped DSP cells and evaluated against the exact critical path. [UG912: `USE_DSP`](https://docs.amd.com/r/en-US/ug912-vivado-properties/USE_DSP) |

## Evidence and limits

AMD 2026.1 UG835 lists `AggressiveFanoutOpt` among `phys_opt_design` directives. UG904 and UG835 describe physical optimization as timing-driven from placed design timing data, so “pre-route” here means post-placement and before routing. The earlier workspace check established command acceptance in the prior flow, not support in every future Vivado build and not QoR improvement on the new candidate. No 2026.1 invocation or hardware/native run was performed for this note.

The next adaptive result should therefore decide the question: if the critical path remains high-fanout and net-delay dominated, the existing fanout directive is a scoped A/B; if the new route instead shows low-fanout long net delay, deep LUT logic, or a DSP boundary, do not spend the remaining adaptive trial on blind fanout replication. Keep all existing constraints, clock definitions, and properties unchanged.
