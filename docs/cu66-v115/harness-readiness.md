# V115 harness readiness: existing integrated RTL seam

Read-only discovery found reusable tests at each layer and an existing one-frame RTL simulation that connects the real QSPI endpoint/CDC to the real JPEG core and display path. There is still no connected Sunshine → Rust firmware worker → QSPI pin stimulus run. The test boundaries below are explicit; testbench-driven QSPI pins are not output from target firmware.

| Layer | Existing entrypoint | Actual coverage and boundary |
| --- | --- | --- |
| Sunshine native serializer | `GameBubMsv1.PacketsMatchPinnedReceiverFixtureByteForByte` in the sibling Sunshine checkout; run its existing `test_sunshine.exe --gtest_filter=GameBubMsv1.*` from the build directory. | Calls native `packetizer_t` on the pinned pre-encoded JPEG and compares every MSV1 byte to a golden. No capture, encode, send, or negotiation. |
| Rust receiver parser | From Moonbub root: `python3 scripts/integration_checks.py`. | Compiles actual `firmware/handheld/src/streaming/protocol.rs` and invokes `Header::parse`, `Receiver::accept`, and `feedback` in a host wrapper. The retained result reports 1,394 cases and 26 JPEG chunks, but it is stale for the current script: `integration_checks.py` calls `packets(jpeg, 100, ...)`, which implies 262 chunks and 1,630 checked cases. The result does not pin the script SHA, so treat those counts as historical. The wrapper uses Python packetization; it does not execute ESP-IDF, `streaming::session`, DMA, or SPI. |
| QSPI pins and CDC | `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test_qspi.ps1 -StartPhaseNs 0`. | Exercises real `moonshine_qspi_endpoint` and `moonshine_bus_cdc`. Its downstream core register/FIFO model is behavioral, so this is not JPEG decode. |
| QSPI → JPEG → memory/SDRAM → LCD | From Moonbub root: `fpga/experiments/throughput30/burst/qspi-study/run-jpeg720-verilator.sh`. | `tb_qspi_jpeg720.sv` drives QSPI pins into the actual endpoint and CDC, wired to the actual 720×480 JPEG core, tile transpose, burst memory/SDRAM path, and LCD scanout. It sends the checked-in 26,159-byte q65 JPEG in 26 chunks, checks all 345,600 decoded coordinates/SDRAM words, 43,200 bursts, one presentation, zero LCD underruns, and zero CDC loss. The recorded Verilator 5.020 run reports 140,045 upload cycles and 2,449,960 commit-to-presentation cycles at 100 MHz. It is a real integrated RTL simulation with testbench-generated pin transactions, not Sunshine or ESP32 firmware output. The script uses `-Wno-fatal`; treat it as functional integration evidence, not strict-warning V115 acceptance. No hardware was programmed. |
| JPEG plus SDRAM publication | `powershell -NoProfile -ExecutionPolicy Bypass -File fpga/scripts/test_pipeline.ps1`. | Runs actual JPEG core, memory and SDRAM model on a small 16×16 JPEG and direct core-bus writes. It bypasses firmware and QSPI. A separate `fpga/scripts/test.ps1` runs the 720×480 decoder through direct core-bus stimulus. |

Moonbub and Sunshine hold byte-identical copies of the 720×480 JPEG and MSV1 golden packet fixture: SHA-256 `8cc99ea7…` and `78c58cf…`, respectively. The native Sunshine unit test proves its packetizer emits the same fixture. The current Rust integration script source feeds real JPEG-derived packets to the production parser, but its retained result is stale relative to its current 100-byte chunk setting and must be refreshed before use. The tests do not pipe C++ output directly into Rust; the old stored Rust harness has a Windows absolute source path and reads u32-framed input, while the shared packet fixture is u16-framed.

## Remaining V115 integration gap

The production firmware worker in `streaming/mod.rs` calls the actual receiver, then `begin`/`forward` and the FPGA `spi_write` API. The qspi-study simulation already exercises the coupled endpoint/CDC → JPEG → memory/SDRAM → LCD path, while `moonshine_top` is the production wiring reference. Its QSPI transactions are manually generated in a testbench; neither Sunshine packetizer output nor the Rust worker/ESP-IDF SPI callsite drives them. A concrete next handoff is to feed the exact MSV1 datagrams through a host wrapper around the production Rust parser and a protocol-to-QSPI transaction adapter that drives this existing bench's pin tasks, preserving real RTL downstream. The adapter would be new work and must not be described as target firmware integration. Keep the known `-Wno-fatal` warning policy visible; no hardware was programmed and no full Sunshine → target firmware → display claim is supported.

Fixture hashes, exact source paths, retained result pins, tool dependencies and commands are in [`harness-readiness.json`](../../experiments/python-gamebub-v115/inventory/harness-readiness.json). External Sunshine instructions were read from its `AGENTS.md`; its native build expects Windows MSYS2 UCRT64, CMake/Ninja and the experimental feature enabled.
