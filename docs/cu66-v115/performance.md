# V115 cycle ledger

The V115 ledger is generated by `scripts/cu66-v115/performance.py` only after
`spatial/results.json` selects a complete actual RTL PASS. Until then, no JSON
or CSV measurement result is written. This parser runs no simulation or native
implementation job.

The baseline is the retained V114 optimized component and transport proof, bound
to all 18 source origins and the selected proof hash in the V114 B125 native
receipt `521daae4…`. B125 identifies a requested native clock and its source
composition; it does not establish an achieved 125-MHz clock. V113 remains the
frozen canonical output oracle. Compressed canonical artifacts, selected
summaries, raw receipts and simulation transcripts are hashed in the ledger.

For each of seeds 107601/107602, the parser matches six complete successful cases
under two service profiles in both the component and actual V97 transport
transcripts. The resulting 48 rows contain 24 component and 24 transport
case/profile measurements. Negative frames are excluded. Each transport report
is paired with its immediately preceding successful case; the two successful
abort/reset retries per seed have no normal transport report and are excluded
from the latency distribution.

`done_cycle - first_input + 1` measures the first accepted **decoder** byte through
component done, inclusive. It does not start at host capture, at the first byte
accepted by V97, or at first QSPI reception. Last canonical pixel uses the same
start. The separate transport `elapsed_cycles` measurement begins at transport
startup and includes command/prefill work through report time. Ingress commit
and decoder done remain separate fences. No complete C2/HUD seal, full-parent
publication, display handoff or sustained hardware campaign is timed here.

The IV115.1 candidate adds two inverse helper preparation edges per normal tile,
eight ingress SELECT edges per compressed packet, and scratch begin reservation
at E with commit at E+3 plus read-tag preparation. These stages shorten timing
cones at a potential cycle cost. Their work overlaps with other stages and
stalls, so the whole-case difference is measured rather than inferred by adding
local bubbles. Profile 0 uses deterministic fast service. Profile 1 retains its
seeded service policy, but changed scheduling can shift the random draw times;
its deltas are observations rather than a controlled single-path experiment.

At an assumed 125 MHz, 10 ms is 1,250,000 cycles. Strictly under 10 ms therefore
requires fewer than 1,250,000 cycles; a zero margin is insufficient. At the same
assumed clock, one 30-fps interval is about 4,166,666.67 cycles. These arithmetic
budgets do not validate timing, sustained frame throughput or complete decode.
The JSON explicitly keeps achieved-clock validation, hardware 30 fps and
validated complete under-10-ms decoding false. Native route evidence is reported
separately.

## Selected actual results

The selected campaign is `20261109T010347118399Z`, with complete actual component
and V97 transport verdicts for both seeds. All 48 measured successful rows have
518,400 canonical samples and match the frozen V113 canonical output hashes.
The selected V115 summary SHA-256 is
`52697a476f23ec0c44c17fc80026daeb63755d5481f2c360c8af9b4f557fc907`;
its raw receipt SHA-256 is
`fb381cd142dfb9c4712bf8dacb280b45555859591af264bde244fa8f4ccff573`.
The generated JSON pins 27 selected inputs, including all eight timing
transcripts and the canonical artifacts of all three generations.

All cycle values below use first accepted decoder byte through decoder done.
Each row represents 12 matched successful case/profiles, across both seeds.

| Run and service | V114 B125 min / median / max cycles | V115 min / median / max cycles | Conditional V115 range at 125 MHz |
| --- | --- | --- | --- |
| Component, fast | 642,491 / 1,012,911 / 1,383,951 | 642,491 / 1,012,922 / 1,385,090 | 5.140–11.081 ms |
| Component, stalled | 1,761,386 / 2,085,147.5 / 2,466,887 | 1,761,769 / 2,084,934 / 2,463,418 | 14.094–19.707 ms |
| V97 transport, fast | 642,491 / 1,012,911 / 1,383,951 | 642,491 / 1,012,922 / 1,385,090 | 5.140–11.081 ms |
| V97 transport, stalled | 1,758,873 / 2,079,216 / 2,451,097 | 1,758,269 / 2,079,579 / 2,449,971 | 14.066–19.600 ms |

Fast-service per-case changes range from zero to +5,530 cycles, with median
+11 cycles. The critical-cone preparation has therefore preserved the broad
service budget while adding a measurable cost to some frames. Under stalled
service, component changes range from −5,202 to +2,024 cycles and transport
changes from −3,117 to +2,209 cycles; these include the scheduling effect of the
same seeded service policy.

Eight of twelve fast-service rows in each run type are arithmetically below
1,250,000 cycles; four exceed the threshold. No stalled-service row is below it.
Consequently even the conditional component calculation does not satisfy the
under-10-ms goal across this corpus. Every observed component and transport
case fits a 30-fps interval **if** the clock really operates at 125 MHz, but this
is service headroom rather than sustained hardware 30-fps evidence. The JSON
and CSV retain each case identity and its exact cycle margin for the next
throughput optimization.
