# V79 continuous system monitor

V79 forks the V78 C++ system bench and keeps the V78 source list, `cu78_system_sim` top, and every HDL byte unchanged. Native packet decoding supplies independent expected canonical planes and display pixels. Actual FPGA decoding writes canonical storage; actual modeled SDRAM commands provide HUD write/readback and direct native LCD scanout. The scoreboard never seeds canonical or display memory.

Every call to `d.eval()` goes through the V79 observer. That includes scheduled HDL timing events, pixel edges, memory/read clock edges, reset initialization, fixed-release waits, start-readiness waits, transactions, canonical-memory peeks, and the final tail. `lcd_error`, nonzero `lcd_memory_errors`, and nonzero `lcd_underruns` latch a sticky failure and immediately reject the run. Diagnostics identify the simulation time and the current phase: `reset`, `release_wait`, `readiness_wait`, `transaction`, or `final_tail`. There is one initialization reset per cohort and no per-source reset or fault clear.

Each actual receiver `done`/global commit acknowledgment records exactly one obligation for that generation to complete a correct 480×800 physical raster within 10,000,000 memory cycles (100 ms). A full raster already observed before ACK satisfies the obligation immediately. ACK retries cannot extend the deadline. The bench tracks only unfulfilled obligations in the hot monitor; historical timing records remain available for the final report. Deadline failures identify the generation, phase, current cycle, and due cycle. This deliberately conservative bound is a **functional liveness check**, independent of the 30 source fps and validated-under-10ms performance criteria.

A successful source raster requires all 800 ordered rows and 480 ordered columns per row to match its native expected pixels, including black borders, while holding one generation. Every requested source must have a distinct complete correct raster before terminal `SYSTEM_PASS`. Monitoring continues for at least 3,500,000 cycles after the last ACK, extending until all raster obligations are satisfied. A failure cannot disappear in the release, readiness, or final-tail gaps.

Fixed30 releases are the immutable finite schedule `initial_cycle + floor(ordinal × 100000000 / 30)`. The complete requested cohort schedule is known before traffic begins. At each observed simulation time, released sources are counted from that schedule, including releases occurring while the current source waits for readiness. `max_waiting_released_unadmitted` measures released minus admitted; `max_in_service` measures admitted minus ACKed; `max_total_released_unacked` measures released minus ACKed. `max_input_queue` is retained as an alias for the waiting maximum. The finite cohort caps arrivals. Paced mode releases each next packet when its preceding bench call completes. Neither mode moves an original fixed-release timestamp to hide waiting.

The global memory-cycle watchdog is explicitly `108 + requested_frames × 110000000 + 10000000`. Readiness, admission, and frame transactions also have finite 100,000,000-cycle guards. The runner applies an in-container `timeout` of `600 + requested_frames × 120` wall seconds, with a 10-second kill grace and a larger client timeout. These generous diagnostic bounds do not qualify target throughput.

Per-frame `base{0,1}_tile{0,1}_aux{0,1}_cycles` partition transaction memory-clock ticks into eight disjoint bins. `base1` means receiver stage 5 (`BASE_RUN`); tile and auxiliary flags sample their corresponding memory-busy signals at tick entry. `stage0_cycles` through `stage15_cycles` partition the same ticks by receiver stage. Both families must sum exactly to the frame's transaction cycle count. They are observations of overlap and occupancy; they do not identify a causal critical path by subtracting overlapping counters.

Build once in `gamebub-cu66-v69-build` with `-j 1`, then share its immutable executable across independent cohort runtime jobs:

```sh
python3 scripts/cu66-v79/run_system.py --cohort 0 --frames 4 --mode fixed30 --tac 2
python3 scripts/cu66-v79/run_system.py --cohort 0 --frames full --mode fixed30 --tac 2 --skip-build
python3 scripts/cu66-v79/run_system.py --cohort 1 --frames full --mode fixed30 --tac 2 --skip-build
python3 scripts/cu66-v79/run_system.py --cohort 2 --frames full --mode fixed30 --tac 2 --skip-build
python3 scripts/cu66-v79/run_system.py --cohort 3 --frames full --mode fixed30 --tac 2 --skip-build
```

The index contains 119 chronological sources in each of cohorts 0, 1, and 2 and 100 in cohort 3. `--frames` also accepts 2, 4, and 30; `--mode paced` and `--tac 7` remain supported. The binary path is `/build/v79-system-tacN/Vcu78_system_sim`. `system/build-tacN.json` records its SHA-256, source identity, and original build commands. `--skip-build` verifies that identity and performs no build. Each run pins all native fixture packets from the full index, all native headers, all V78 RTL/includes/source-list bytes, the V79 bench, monitor, and runner before execution and verifies the source pins again after successful execution. Existing result paths must be archived before a rerun.

Results live under `system/cohortN-framesCOUNT-MODE-tacN/`. Each command records its argv, log digest, exit code, timeout, and wall time. A functional failure retains logs and writes `status: FAIL_FUNCTIONAL`. A pass requires a unique terminal `SYSTEM_PASS`, every requested `SYSTEM_FRAME_PASS` and `SYSTEM_TIMING`, complete rasters for every source, zero sticky display-health observations, zero underruns/black lines, expected actual memory traffic, and no RGB framebuffer writes. Performance remains a separate `performance.status`; a functional pass can coexist with performance `FAIL`.

`python3 scripts/cu66-v79/run_monitor.py` runs nine small observer-unit checks in the existing build container. Its `monitor-tests/` evidence covers LCD error pulses in release/readiness/tail, memory-error increments, underruns, expired raster deadlines, fulfilled and pre-ACK-complete rasters, finite arrival growth during readiness, and the full-cohort global watchdog. These checks use synthetic `FakeOutputs` and exercise verification logic only: `observer_unit_only=1`, `hardware_fault_injection=0`. They do not demonstrate hardware fault recovery or substitute for the actual-system campaigns.

This evidence remains finite functional simulation with native HUD CPU work at zero simulation time. It does not prove live ESP32/Wi-Fi/QSPI behavior, physical 30 fps, validated target decode under 10 ms, target fit/Fmax/CDC, or electrical timing.

The first cohort-0 four-source fixed30/TAC2 smoke passed functional qualification: four distinct complete source rasters, 234,828,935 health observations, zero display faults/underruns/black lines, and no RGB framebuffer writes. Build wall time was 20.606 s; runtime was 73.147 s; total runner wall time was 93.897 s. All preexisting V78 frame fields, timing fields except native HUD CPU wall time, and summary fields matched the corresponding V78 four-source run exactly, including 16,087,581 cycles and 3,632,257 observed pixels. The additional observer did not alter modeled event timing.

The same smoke reported performance `FAIL`: serial30 met for all four sources, while modeled packet-complete-to-validated latencies were 14.08760, 28.76078, 26.41404, and 25.87469 ms. These are simulation results, not target timing proof. Full cohort campaign results are recorded separately by the campaign runner and evidence audit.
