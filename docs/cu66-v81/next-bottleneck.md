# V81 next bottleneck: shared memory service and reference readiness

The 128-bit fill does not materially improve the bounded end-to-end replay.
Do not spend the next iteration increasing inverse-transform lanes merely
because the base FSM is named `WAIT_IDCT`: most of that state's predicted-frame
time holds an already completed inverse result while reconstruction is not
ready. The highest-value next experiment is bounded reference lookahead and
memory command admission, with explicit ownership and display-service checks.
A separate bridge/controller service change or physical-traffic reduction is
needed for the under-10-ms goal under the current observed delta traffic.

## What was measured

[`profile-analysis/results.json`](../../fpga/experiments/cu66-v81/profile-analysis/results.json)
is generated by:

```sh
python3 scripts/cu66-v81/analyze_profile.py
```

It pins four completed bounded main runs, their compressed/raw traces, the two
read-only diagnostic runs, the analysis script and relevant architecture source.
It recomputes busy-bin partitions, physical command counts, packet-to-validation
milestones, address-reuse screening and all predecessor-type command gaps.
Whole trace windows include post-ACK LCD work; admission-to-ACK counts come
from the original per-frame JSON and are kept separate.

The read-only diagnostic top is `profile/cu81_profile_sim.sv`. It instantiates
the same frozen `cu81_system` and SDRAM model as the main experiment and only
exposes hierarchy observations. Its copied positive bench retains original
packet, reference, hash, canonical/HUD and complete native raster checks.
Both cohort-0 and cohort-3 four-source replays pass, with **every original
frame/timing/summary field identical** to its main-run control, except native
CPU wall time and trace-row count. The runner checks this equality before PASS.
No diagnostic drives an internal signal or changes the clock/reset schedule.
The recorded schema retains the system-run producer version; `profile_frames`,
`control_equivalence`, source-list top, and the `profile/` location identify the
additional verification-only experiment.

Reproduce the diagnostic runs sequentially:

```sh
python3 scripts/cu66-v81/run_profile.py --cohort 0
python3 scripts/cu66-v81/run_profile.py --cohort 3
```

Each run builds with one job into its own immutable Mdir, records source

### Inverse execution versus held output

These are observed clock counts in each source's existing transaction window,
not sums of exclusive recoverable delay. The window ends at CPU ACK and excludes
an earlier admission queue. Clock conversion assumes 100 MHz.

| Inverse arithmetic states 1–8 | 404,088 | 499,020 |
| Inverse `OUTPUT_TILE` | 1,767,792 | 1,738,304 |

Across the three predicted sources, held inverse output ranges from 1,678,406
to 1,759,692 regular cycles, and 1,623,013 to 1,909,078 combat cycles. It is
not arithmetic execution. The keyframes instead have zero output-valid/not-ready
cycles, with 392,568 regular and 623,332 combat inverse arithmetic cycles.

Source inspection explains why reference readiness is a concrete hypothesis:
`idct_out_ready` requires `recon_ready`, while reconstruction requires either
key/hidden status or the leased reference sample. The base already accepts the
next tile and can compute it while a previous candidate write is pending; it
is not a completely sequential decode-then-store frame architecture. The current
profile records write-pending joints and reference predicates, but does not
record every joint of inverse hold, reconstruction slot readiness and missing
reference. Add that exact joint before attributing every held cycle to reference
supply. Never call all `WAIT_IDCT` cycles DSP work or claim all held cycles are
removable.

Controller/bridge IDLE counts and request-valid/not-ready counts also overlap
other work. They do not prove that a useful request was eligible at every idle
clock. Hash `busy` spans much of frame processing, while rows-not-ready at the
write fork is small in these samples; neither observation proves that hash
optimization has no value in another workload.

### Physical work remains substantial

Each predicted source still performs 32,400 canonical-write blocks, 32,400
reference-read blocks, and 2,640 HUD writes plus 2,640 HUD reads. Those are
70,080 non-LCD BL8 commands and 1,121,280 transferred payload bytes. This includes
518,400 canonical bytes, 518,400 reference bytes and 84,480 HUD read/write bytes.
The ideal x16, one-word-per-100-MHz-clock payload-only time is 5.6064 ms; it
excludes all commands, refresh, row changes, recovery, turnaround and display
work. It is not a predicted latency or a measured target bandwidth.

Regular predicted source 1 performs another 66,288 LCD read commands, for
136,368 total accepted physical commands and 2,181,888 payload bytes in its
transaction window. Combat source 1 performs 82,929 LCD reads in the wide
variant, for 153,009 commands and 2,448,144 payload bytes. The original packets,
resolution and physical display continue unchanged.

### A conditional service lower bound for the frozen design

The unchanged V74 bridge owns one physical transaction until its response is
retired. The following edge ledger assumes a row hit, no refresh, an unstalled
response and another eligible client. `E0` is the physical controller request
acceptance. It deliberately uses the fastest path, rather than a measured
average or an address conflict assumption.

| Read predecessor | Write predecessor |
|---|---|
| E0 accept; E1 `RW_CMD` | E0 accept; E1 `RW_CMD`/word 0 |
| E2…E7 `READ_WAIT`, first response registered at E7 | E2…E8 `WRITE_BURST`/words 1…7 |
| Bridge captures response words at E8…E15 | Recovery WAIT at E9…E12 |
| E16 bridge response accepted | E13 bridge observes controller idle |
| E17 next bridge client accepted | E14 bridge response accepted |
| E18 next physical command accepted | E15 next bridge client accepted; E16 next physical command accepted |

The LCD stream also cannot deliver its final captured word before E16. Thus
successive physical accepts in this frozen service path are separated by at
least 18 clocks after a read or 16 after a write. The script checks every raw
command predecessor interval in all four selected traces; observed minima are
exactly 18 and 16. That observation corroborates the source walk, but is not a
formal verification proof.

For the observed no-cache-hit delta traffic, ignoring LCD entirely and dropping
the final predecessor's maximum 18-clock interval gives:

```
35,040 reads × 18 + 35,040 writes × 16 − 18
= 1,191,342 clocks = 11.91342 ms at the assumed 100 MHz
```

All mandatory writes and HUD readback fences must precede validation. Therefore
more inverse lanes or more reference slots alone cannot make this same fixed
physical-traffic/frozen-service configuration validate in under 10 ms. This is
a **conditional structural bound**, not physical timing signoff, formal proof,
or a universal lower bound on the codec. It changes if cache hits, skipped
stores, traffic volume, bridge admission, controller pipelining or clock changes.
LCD, refresh and row misses only add work to this qualified accounting.

## What not to prioritize: a small generic shared read cache

The current P0 read cache has zero hits in these main runs. A read-only physical
address replay screened a hypothetical fully associative LRU cache shared by
LCD and reference reads, invalidating on every observed physical write. It
keeps actual command order and timestamps unchanged, resets once per recorded
run, and does not remove, reschedule or simulate any work.

| Cache data only | Regular wide combined address hits | Combat wide combined address hits |
|---|---:|---:|
| 128 B | 14 / 429,916 (0.0033%) | 11 / 424,118 (0.0026%) |
| 8 KiB | 1,182 / 429,916 (0.275%) | 1,513 / 424,118 (0.357%) |
| 32 KiB | 5,504 / 429,916 (1.280%) | 6,842 / 424,118 (1.613%) |
| 128 KiB | 25,152 / 429,916 (5.850%) | 30,336 / 424,118 (7.153%) |

All 97,200 distinct reference block addresses also appear in LCD reads, but the
access order/reuse distance makes a small generic cache ineffective in this
screen. Metadata, comparator cost, cache fill/lookup latency, replacement timing
and actual hardware fit are not modeled. These hits are neither proven usable
RTL hits nor a speedup prediction; they are a reason to avoid assuming that a
small shared cache will solve the problem.

The same trace screen records successive same-bank address row changes. In the
wide regular/combat windows, reference↔LCD transitions change row in
33,624 / 33,704 and 50,703 / 50,808 comparisons respectively. Canonical↔HUD
transitions change row in every 16,974 regular and 11,922 combat comparison.
These are physical-address-order observations, not actual controller row-hit
counters; refresh and eligibility are not represented. They support measuring
row-local arbitration opportunities, not subtracting all PRE/ACT counts as
recoverable time.

## Next controlled experiments

1. Add exact predicates for inverse hold with missing reference versus held
   reconstruction slot, prefetch request blocked by slot capacity versus memory
   admission, and simultaneous eligible client requests at each bridge decision.
   Count actual controller row hits/misses, refresh and read/write recovery
   separately. Retain source generation and command-owner identity.
2. Try four then eight bounded reference slots, holding all generation/bank/plane/
   tile leases and existing authenticated retirement rules. Compare against the
   two-slot wide and V80 overlap controls at identical releases and display
   phases. This tests lookahead and burstiness, not a promise of proportional
   speedup, and cannot by itself break the conditional service bound above.
3. Prototype an explicitly bounded next-command descriptor queue and saved
   response buffers in a separately versioned bridge/backend. Admit a next
   eligible request while an owned command finishes, so ownership, response
   backpressure and fences do not require a fresh post-response admission cycle.
   Also test short same-row command groups (1/2/4) within strict LCD and HUD
   service bounds. The tile adapter currently offers the next block only after
   its previous response; its accepted-command/response accounting must change
   deliberately if more than one block is admitted. Preserve exact physical
   order, write recovery, error drain and read/write cache invalidation rules.
4. Keep a separate longer-term traffic-reduction path, such as application-aware
   unchanged-tile storage reuse, with a measured unchanged-tile fraction and a
   bounded page/map/refcount model before RTL. It must not replace a required
   canonical store with a fictitious completion. Reference and old-display
   lifetime must survive abort, retry, keyframes and bank recycling.
5. Require both SDRAM corners, strict lint, held data/tag and simultaneous-event
   cases, actual reject/abort/retry, paired canonical/HUD/full-raster checks,
   then all four histories for any candidate. Report regressions as well as
   gains. Close sustained 30-fps qualification before claiming the later strict
   maximum under-10-ms milestone; neither follows from this diagnostic study.
