# V91l bounded tile-row write comparison

This follow-up compares the frozen byte-at-a-time candidate writer with one
bounded eight-byte row owner in the actual live BR88 reconstruction, candidate
memory, C2/HUD/seal hashing and validated-publication path. It changes neither
codec bytes nor intended canonical/HUD pixels. Both static builds use the same
source-backed key/delta chain, service rules and exact byte/hash oracles.

The new adapter gathers one canonical tile row or aligned HUD row, requests its
write, retains its physical-service lease until a matching response, and then
delivers the eight bytes to hashing in original order. It has no second row or
gather/delivery overlap. Its logical payload storage is eight bytes versus the
control's one byte, plus metadata, counts and control; no target RAM/logic fit
or routed frequency is inferred from that allocation.

See the [address/ownership contract](write-contract.md),
[Python model](../../experiments/python-gamebub-v91l-rows/model-results.json),
[standalone RTL audit](../../experiments/python-gamebub-v91l-rows/row-audit.json),
[integrated audit](../../experiments/python-gamebub-v91l-rows/audit.json), and
[summary](../../experiments/python-gamebub-v91l-rows/summary.json).
The qualification results below must come from current-source retained runs.

## Qualified results

Both seeds pass the two static modes with two native frames (c0/f0 key →
c0/f1 delta) and FAST/SLOW service. This is **16 validated commits**, eight
per mode, representing two distinct source frames. Every one of the **16,400
actual RTL SHA-job digests** is independently recomputed. Complete accepted
canonical/HUD banks and captured registered quantizer-cache bytes remain exact.
The delta uses the actual accepted predecessor bank and cache, not fixture data.

| Frame/service | Matched byte-control cycles | Row cycles | Fewer cycles |
|---|---:|---:|---:|
| Key FAST | 3,653,297 | 2,314,551 | 36.64% |
| Delta FAST | 3,329,414 | 2,045,469 | 38.56% |
| Key SLOW | 5,780,185–5,782,524 | 2,563,338–2,563,896 | 55.65–55.66% |
| Delta SLOW | 5,530,855–5,531,395 | 2,350,193–2,350,643 | 57.50–57.51% |

The cycle fence starts at the RTL transaction start and ends at validated
commit. Delta quantizer preload adds 1,350 separately reported cycles. The
comparison is against the fresh width-priced control, not the historical
one-edge candidate-response experiment. Both modes follow identical service
rules; the different request schedules do not imply identical absolute random
stall traces. Per-frame bytes, physical-service counts and every nominal bus
request/ACK/hash-byte event are independently replayed.

Candidate logical requests fall **560,640 → 70,080/frame (87.5% fewer)**,
while modeled x16 candidate payload transfers fall **560,640 → 280,320 (50%
fewer)**. Each accepted frame still writes and hashes exactly 560,640 bytes.
No encoding, quantization or pixel-quality change produces the cycle reduction.

Each seed has **39 integrated entries per static mode**, with some repeated
across profiles; standalone RTL separately passes 32 directed entries and
4,096 generated byte comparisons per seed. Wrong ACKs retain the true pending
owner; matching errors drain without hash delivery. The integrated bus-error
test deliberately writes a provisional prefix before its error response, checks
that the suffix remains unchanged, and proves accepted-bank bytes stay intact.
Cancellation, warm reset, HUD bounds, held presentation and retry remain active.
This is bounded simulation evidence, not formal proof or continuous 30-Hz service.

The separate Python model enumerates the complete canonical address bijection.
A source-pinned controller-FSM model finds six edges between best-case open-row
single-word write accepts. With one additional hypothetical logical ACK edge,
its service-work arithmetic is 3,924,480 edges for byte writes versus 1,752,000
for packed row words. Those values are **not** integrated frame latency and
cannot be substituted for the measured comparison table: they exclude real row
transitions, refresh, reads, arbitration, bridge implementation and byte masks.

## Comparison and physical scope

Candidate-write FAST service charges one x16 data transfer plus one response
overhead edge for a byte request, and four data transfers plus the same one-edge
overhead for a row. SLOW charges each request its data transfers plus two through
seven seeded overhead edges. Request stalls and hash backpressure are finite.
The byte control is the unchanged prior adapter, compiled separately through
the static wrapper; this is a new matched-service comparison. Prior published
FAST counts used a different candidate response delay and are historical controls,
not the denominator of this speedup.

This x16 pricing applies **only to candidate writes**. The frozen scratch and
reference actors remain independently serviced logical endpoints. In particular,
the reference actor returns a 64-byte tile in FAST eight or SLOW 12–24 edges;
that is not a 32-transfer x16 physical read schedule. The scratch actor exposes
128-bit requests with its frozen FAST/SLOW latency. They do not share bandwidth
with candidate writes or display traffic in this checkpoint. Full-path simulation
cycle counts therefore describe this declared model, not an achieved physical
memory schedule or a hardware clock requirement.

The existing [SDRAM RTL](../../fpga/rtl/moonshine_sdram.sv) uses a 16-bit word
request interface, BL8 reads and **single-word writes** (`13'h233` mode register),
with explicit waits and refresh. An eight-byte row needs a bridge issuing four
word writes and paying each command's waits, or a separately qualified new burst
write mode. The current controller has no byte-enable request port; the byte
baseline also needs an explicit masking/RMW policy before physical integration.
Four payload beats plus one logical response overhead do not model those command
costs. The separate controller-cost model records the best-case word-service
work assumptions; it is not an RTL controller integration or frame-latency proof.

Native C++ HUD semantic decode and start-header preparation remain before the
RTL start fence. Quantizer preload is reported separately. RTL HUD decode/overlay,
shared physical memory/RGB/scanout, ESP32 service, mapping and hardware measurements
remain open. **Sustained hardware 30 fps and validated decoding below 10 ms are
not established by this comparison.**

## Next implementation gate

Retain both static controls and qualify a row-to-word bridge against the actual
SDRAM controller, including each word command, row hit/miss, refresh, byte masks,
write failure after partial memory effects and accepted-owner drain. Price scratch,
reference, candidate, conversion and display traffic on one finite x16 service
model before making a complete 30-Hz or latency claim. Only then compare bounded
two-row overlap against this single-row control. Actual HUD decoding/overlay and
processor execution/transport accounting remain required parts of V91l/V91m.

## Reproduce

Use the existing `gamebub-cu66-v69-build` container, Verilator 5.020 and GCC
13.3.0. The two comparison modes compile as separate static builds with
assertions, strict warnings, C++ warnings as errors and two compiler jobs.

```sh
python3 fpga/experiments/cu66-v91l-rows/make_wrapper.py
python3 fpga/experiments/cu66-v91l-rows/make_bench.py
python3 experiments/python-gamebub-v91l-rows/model.py
python3 experiments/python-gamebub-v91l-rows/controller_cost_model.py
python3 scripts/cu66-v91l-rows/run_rows.py --seed 912101
python3 scripts/cu66-v91l-rows/run_rows.py --seed 912102
python3 experiments/python-gamebub-v91l-rows/verify_rows.py
python3 scripts/cu66-v91l-rows/run_comparison.py --seed 912101
python3 scripts/cu66-v91l-rows/run_comparison.py --seed 912102
python3 experiments/python-gamebub-v91l-rows/verify_results.py
python3 scripts/cu66-v91l-rows/summarize.py
```

Both generators were also replayed in an isolated dependency tree and produced
byte-identical RTL and C++ sources; the [generation receipt](../../experiments/python-gamebub-v91l-rows/generator-reproduction.json)
pins those inputs and outputs.

The retained binary bus trace is a sequence of 32-byte little-endian records:
`<BBBBIIIIQI`, containing kind, service profile, bank, byte count, fid, epoch,
token, byte address, data and cycle. Kind 0 is a logical write request, 1 its
matching response, and 2 an actual hash-delivery byte. Request payloads, ACK
identity, byte order, timestamp service and accepted-memory exports can be
replayed independently of the RTL model's verdict. The trace contains nominal
frames; fault/rollback evidence comes from the pinned self-checking testbench,
not from pretending the nominal trace includes negative transactions.

The standalone campaign separately tests generated rows, partial filling,
unaccepted offers, pending ACKs, partial hash delivery, reset/cancel on matching
ACK edges, each mismatched ACK field, invalid starts/continuations and retries.
The Python address model enumerates the full canonical address bijection; that
exhaustive address enumeration is not the standalone RTL stimulus coverage.

## Retained failures

The first row compilation caught a strict Verilator bit-parameter width warning
when a 32-bit `-G` value overrode the one-bit selector. Explicit one-bit literals
fix it; no warning was suppressed. A superseded attempt failed the source-freshness
gate after passing simulation. All such attempts remain retained and cannot
qualify the final selected results. Frozen prior controls remain unchanged.
