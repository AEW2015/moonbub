# V41 checkpoint: global raster context, host bottlenecks and fair packet caps

This iteration finds a real synthetic spatial win, identifies the Python HUD
bottleneck and closes the misleading combat gap in the coarse native grid. It
does not demonstrate lower gameplay bitrate than HEVC/AV1. No FPGA or ESP32 code
is changed; the six-hour run continues.

## Global raster context with exact reconstruction

[RR41/GR41](../experiments/python-game-raster-v41-study/README.md) replaces the
SP38 two-by-two prediction reset with global raster top/left residual edges.
Mode selection admits only predictors that reproduce every control YUV sample
exactly. A candidate reaches the selected stream only if its actual complete
packet is strictly smaller than control. The decoder derives its context only
from already reconstructed blocks; host vectorization uses the exact-output
invariant to obtain the same values, not a decoder source oracle.

| Input | Control complete bytes | Selected bytes | Accepted candidate |
| --- | ---: | ---: | ---: |
| Primary gameplay, 12 frames | 134,817 | 134,817 | 0/12 |
| Complex gameplay, 12 frames | 309,308 | 309,308 | 0/12 |
| Flat fixture | 3,095 | 2,683 | 1/1 |
| Directional and noise fixtures | Control retained | Control retained | 0/2 |

The flat fixture saves 13.3118% at zero error. That is an actual serialized
positive witness, not a game-stream win. Gameplay candidates remain larger
(138,677 /313,076 bytes); the actual byte guard retains controls. The broader
context supplies 63,699 eligible nonzero exact alternatives and proposes 20,862
nonzero modes, so adding alternatives alone does not fix the local rate proxy.

Four producer and eight independent tests pass. Independent replay checks 27
selected causal frames, 162 rank trials, 843,048 candidate computations and
218,700 raw edge/predictor frontiers. The logical top/left residual cache is
2,928 bytes under this profile, excluding whole images, coefficient storage,
compressed input, transform buffers and implementation overhead. This is not a
BRAM fit or placed FPGA result. RR41/GR41 needs a new receiver grammar.

## Where Python host time goes

The [six-frame HUD profile](prototype-v41-hud-profile.json), generated by
[profile_hud_v41.py](../experiments/profile_hud_v41.py), reproduces every selected
HUD byte. Instrumented wall time is 2.138667 seconds and raw profiler self time
sums to 2.138403 seconds. Raw entries are explicitly aggregated because frozen
modules loaded under several names share `(filename,line,function)` keys, and
ordinary pstats overwrites some entries. The initial pstats aggregate understated
elapsed work and is not used for conclusions. The corrected Huffman generator
has 2,547,254 calls and 0.727 seconds self time; `format` has 2,731,615 calls and
0.356 seconds self time. `str.join` contributes 0.166 seconds self time.
Cumulative times overlap and must not be added. These are profiling diagnostics,
not uninstrumented paired speed measurements. The next iteration replaces bit strings with packed numeric plans
and materializes only winning representations while preserving exact wire bytes.
That optimization benefits the shared HUD overlay in native and custom paths.

## Native peak-rate controls close the combat gap

The [targeted cap study](../experiments/python-game-native-cap-v41-study/README.md)
adds 21 actual native settings and independently redecodes 2,100 access units.
It retains the same 100 combat sources, exact HUD, 80-byte binding accounting,
extradata, original RGB565 error metric, keys24 and immediate low-delay output.
Eight settings have at least one cap failure; all are retained.

| Combat setting | Complete bytes | Mean active MSE | Maximum packet | Cap failures |
| --- | ---: | ---: | ---: | ---: |
| Custom CS38 | 3,002,785 | 29.3515 | 44,032 | 0 |
| HEVC CRF24, VBV160 | 2,098,348 | 27.5797 | 40,122 | 0 |
| HEVC CRF22, VBV160 | 2,362,563 | 23.9478 | 40,122 | 0 |
| AV1 CBR3000, buffer40 | 2,025,584 | 25.8078 | 39,559 | 0 |
| AV1 CBR4000, buffer40 | 2,302,669 | 21.7033 | 45,038 | 0 |

The HEVC CRF22/VBV160 point uses 21.3209% fewer complete bytes than CS38, fits
every cap, and has no worse source SSE on every individual frame. AV1 CBR4000
passes the mean-plus-peak error gate but not the every-frame gate. The lower-rate
HEVC24 and AV1 CBR3000 points pass mean error only. The
[gate comparison](prototype-v41-native-cap-comparison.json) keeps those claims
separate. There is no native optimality or equal-decoder-hardware claim.

The [x265 VBV documentation](https://x265.readthedocs.io/en/stable/cli.html) and
[SVT-AV1 parameter reference](https://github.com/AOMediaCodec/SVT-AV1/blob/main/Docs/Parameters.md)
provide the requested control meanings; only actual emitted packets establish
the measured cap outcomes. The tested SVT capped-CRF mbr values leave bytes
unchanged at each CRF, so no effective packet bounding is claimed for that mode.
Passing AV1 CBR5000/buffer40 has only 20 bytes margin and cannot be treated as a
production-safe bound on other content.

These results redirect the application-specific work toward a demonstrably
bounded decoder, exact UI, predictable transport admission and low latency. They
do not justify claiming that the current codec beats native HEVC/AV1 bitrate.
Native CPU decoding does not establish that either standard fits this Gamebub
FPGA. Targeted next steps are direct CS38 reception without entropy re-encoding,
one-block arithmetic delivery, whole-plane rate-aware decisions and measured
whole host service. Hardware handoff remains research-gated.
