# Sealed v31/v32 WiFi power-save ownership review

Read-only source/evidence review. No firmware change/build/device query. The selected v31 legacy regression remains the next single physical variable; v32 is a separate CPL1 observer.

Standalone video does not hold power-save off. All application `esp_wifi_get_ps/set_ps` calls occur in streaming/audio.rs Radio. The AV listener is created by video session, but its PS guard remains None until accepted AV `Event::Started` (audio.rs615). This applies to input-only AV too: audio_enabled is assigned afterward from flags. An idle listener/video-only session never enters the guard. SDK5.4.3 esp_wifi.h documents default WIFI_PS_MIN_MODEM; this is SDK behavior documentation, not a current device mode measurement. Video-only leaves the actual mode untouched.

AV start gets actual mode0..2; if nonzero, set0 and get/verify. On entry failure, the generic guard attempts exact captured-mode rollback; a failed rollback returns Error::Restore. On valid AV STOP or500ms lease expiry, queued/dirty audio is discarded/drained first, then restore_ps takes the guard and verifies restoration. Consequently AV STOP/expiry can restore modem sleep while the video worker continues. Duplicate START does not reacquire; nonactive listener has no lease. Normal x increments stream GENERATION, causing AV cancellation/cleanup; that token is cancellation, not proof that WiFi was reset. Session locals drop/join AV before run_network returns and worker disconnects/stops WiFi. Serialized worker owns the same WiFi object. Early WiFi/core/setup failures precede the AV PS lease; a worker panic is marked unconfirmed by join. Reboot is outside this Rust guard lifetime and establishes no retained-radio restoration continuity.

Concrete failure gap: audio.rs restore_ps takes the guard before finish. STOP/expiry finish failure sets only local ps_unavailable and increments PS_RESTORE_ERRORS through Radio::report; global RECOVERY_FAILED need not become true. Final cleanup then calls restore_ps(None)=true. Guard::Drop may join successfully and call core_access::av_drained(true), whose actual adapter sets power_restored=true along with the other drain bits. Enter rollback Error::Restore has the same counter/local-only gap. This is a source-level safety/reporting defect; no retained hardware run demonstrates it occurred. A fresh AV worker also initializes ps_unavailable=false, so the local latch alone cannot preserve failure across reconnect.

Smallest justified successor: in the existing Radio::report Stage::Restore error branch, retain the counter and additionally set global RECOVERY_FAILED Release. This covers explicit STOP, lease expiry, cancellation/final cleanup, failed enter rollback and guard Drop paths without changing successful radio calls or SDK defaults. Actual Guard::Drop then passes false to av_drained; actual coordinator retains AV ownership and quarantines. No command clears that sticky failure. Add exact-production-fragment fake-SDK tests for set/get/verify restore faults, rollback faults, later empty cleanup, join and coordinator proof rejection; retain happy input-only/STOP/expiry/allinitialmodes. Root authorized isolated v33 after this finding; sealed v31/v32 stay unchanged.

Separate future behavior experiment: selected v31/v32 do not include the already isolated v28 opt-in video NoPS scope. A minimal later behavior A/B should keep default KeepExisting, sample choice once per next session, acquire NoPS after actual WiFi-up and before AV, restore only after confirmed AV teardown while same serialized radio remains online, and quarantine failed/unclosed owners. Do not use normal stream-generation change as a radio-reset fence. The v28 implementation/tests are a review reference, not automatically adopted source. No evidence yet warrants globally forcing NoPS or attributing Sequence drops to power-save.
