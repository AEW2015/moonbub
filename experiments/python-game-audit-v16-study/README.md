# Python Game v16 evidence audit

Read-only evidence audit for v16. The target remains 720x480 coded, 720x405 active, and 30 fps. Missing finalized studies remain pending; malformed results, failed replays, missing source pins, or hash mismatches are invalid. The retained `audit.json` is populated by `python audit.py`; `python audit.py --check` recomputes and compares without writing it. Neither command runs study benchmarks.

The finalized golden pack independently replays 10 AR02 frames and 12 GF02 datagrams, verifies 768 selected RGB565 words, and checks 10 rejected packets for state atomicity. It validates all 84 content-addressed fixture objects (89,759 stored bytes), 26 source pins, and the seven-test study log.

The decoder budget retains 18 actual packet traces, one analytical dense case, 57 conditional scenarios, 52 clock sweep points, and 23 source pins. Its capacity sum is 5,042,080 bytes. The report preserves the study's explicit assumptions about memory service, entropy scheduling, implementation buffers, and scanout. It marks every line deadline and hardware-fit claim unproven; the average service model, local RTL handshake observations, and hypothetical clock sweep do not establish board timing or fit.

The refresh audit rechecks six runs over the same 180-frame manifest, all four exact UI patches (21,120 selected words per decoded frame), resource drains, full-frame caps, and publication/reference invariants. It keeps strict presentation counts separate from five-second unique-image rates. For example, the initial-key-only control is 174 strict / 177 eventual and 29.8 distinct modeled IDs/s; refresh-30 is 158 / 160 and 26.6; repeated refresh-30 is 160 / 162 and 26.8. These are finite model outputs, not live capture rates. A hash-bound untimed comparison finds 152,754 versus 128,210 complete bytes across five matched independent refresh keys, with a 0.3719 increase in common decoded source RGB565 MSE. The key-only comparison does not show a net-wire or lossless gain because future reference histories differ. The frames reuse a v15 regression window and are not fresh held-out validation.

The inline-tag study replays 20 canonical tag cases, including eight 720×480 cases. It confirms an 11,520-byte eight-row stripe and the unchanged 1,036,804-byte SHA input. Removing the separate 518,400-byte packed reference-tag reread is a future-decoder counterfactual only: the producer reads already reconstructed full planes, so the current decoder does not remove that reread. The conditional nominal/optimistic promoted-P planning times remain 60.691/33.815 ms, both above the 33.333 ms frame budget; SHA work is unchanged. This is tag-order and bounded-stripe evidence, not decoder fusion, measured bandwidth, or hardware timing.

The ESP32 gateway audit separately verifies 13 firmware/build source pins and 32 bounded port-sensitivity cases, plus 20 link/burst points and three RAM scenarios. Source facts include 240 MHz configured CPU, no enabled PSRAM, MSV1 JPEG-only transport (no AR02/GF02 support), one 1,065-byte DMA working packet, six UDP mailbox entries, 16 KiB streaming and 20 KiB main stacks, QSPI clock caps, and try-lock/drop behavior. A two-entry command queue is not two reassembly frames. Its modeled CPU costs, link schedules and SPI service remain assumptions, not firmware execution or measured goodput.

The nominal initial-only port scenario completes 176 strictly within the six-second window and all 177 admitted frames after drain, with maximum modeled age 43.547 ms and required mean IPv4/UDP service 6.019856 Mb/s. Eight-packet bursts complete 0/177 and fill/drop 460 mailbox arrivals. A 60-frame maximum-size stress needs 12.57984 Mb/s; at assumed 8 Mb/s, 38 complete strictly and all 60 after a 3.146-second drain, with 1,178.845 ms maximum age. The 275,545-byte RAM reserve is illustrative; every scenario leaves fit unproven. Separate checks reproduce the corrected lock paths: a fresh begin-lock failure has zero abort work, while a mid-frame failure charges abort/retry and increases modeled mailbox drops. Transport queue drain is kept separate from protocol drain, and the firmware's 500 ms idle-frame timeout is explicitly not simulated.

All five study inputs now verify. Their retained test logs total 49 passing study tests; eight additional audit guards pass. The audit records 126 source pins across the five studies, including conservative snapshots of related ancestry that are not all executed by each replay. Cycle-model outputs do not establish measured hardware throughput, and neither host FPS nor finite Python schedules prove physical live 30 fps.

The audit guard suite has eight passing tests. Gateway source facts and the generic cycle model are checked separately; neither is promoted to a hardware qualification.

Run `python audit.py` to refresh the populated audit report, `python audit.py --check` to compare without writing, and `python -m unittest -v test_audit.py` to check audit guards. Use the project virtual environment because the replay tools use NumPy.
