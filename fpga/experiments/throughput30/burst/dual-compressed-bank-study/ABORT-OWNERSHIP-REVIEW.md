# Dual-bank abort and ownership review

This note reviews the isolated experimental `bank-storage-rtl` and test-only `live-qspi-banks` adapter, not production firmware or a hardware implementation. It records directed evidence and unresolved interface obligations; it does not claim a reachable production failure or a proof of cross-clock safety.

## Observed behavior and limits

In `bank-storage-rtl/two_bank_control_storage.sv`, one global receiving transaction owns one bank; the other can be READY, DECODING or PENDING. `abort_valid` or `ingress_overflow` frees only the current receiving bank, and receive abort has priority over begin/data/commit. Independently, an already pending frame may publish on `vblank` in the same clock. The controller does not interpret abort as cancellation of READY, DECODING, PENDING or the front frame. Decode completion releases the compressed bank only after modeled publication, not immediately after decode.

The ownership directed test explicitly checks receive-abort coincident with a different pending frame's vblank, and simultaneous receive-abort plus decoder failure. It also tests CRC, short and oversize rejection, overflow and busy behavior. Storage tests cover two-bank concurrent read/write, 48 KiB boundaries, ownership and reset cases. The separate serialized live guest/QSPI test checks a 25,600-byte aborted frame, intact prior front and later distinct-frame recovery, including full modeled canvas scans. In that live bench `ingress_overflow` is tied low, a detected CDC overflow is fatal, and the adapter's per-chunk fences and stop-and-wait acknowledgments serialize traffic. These observations do not cover asynchronous reset ordering, delayed/stale commands, ambiguous ACKs, transport overflow recovery, or actual CPU, memory, QSPI and display timing. Details and logs are in `ownership-rtl/README.md`, `bank-storage-rtl/README.md` and `live-qspi-banks/README.md`.

On this review, re-running the previously built local `Vtb_two_bank` and `Vtb_two_bank_storage` executables completed successfully: `TEST_PASS_TWO_BANK accepted=7 dropped=8 writes=49185 final_front=60` and `TEST_PASS_BANK_STORAGE reads=51715 overlap=1024 cap=49152 final_front=60`. These are reruns of existing executables, not fresh builds or new independent tests; recorded source hashes and full original runs remain in their `results/` directories.

## Unresolved protocol hazards and required decisions

1. **Stale commands can target the wrong receive.** DATA, COMMIT and ABORT carry no bank, frame ID or allocation generation into the controller. An old delayed abort/byte/commit after bank reuse acts on whichever transaction is currently receiving. An abort with no active receive is silently ignored; it does not return an identified outcome. Define a monotonically changing bank generation/transaction token and require matching token, byte sequence/offset and explicit accepted/rejected response for every operation. Specify token wrap, retransmission and duplicate handling, including what happens when an acknowledgment is lost.
2. **Accepted control is not an end-to-end acknowledgment.** The live bench's adapter forwards raw register writes and increments its `received` fence on each data-register write; that count is not the storage controller's accepted-byte counter or durable-memory acknowledgment. The testbench treats `reject` and CDC overflow as fatal and checks fences, but this is not a recoverable firmware protocol. Expose distinct accepted BEGIN/DATA/COMMIT/ABORT results with identity, committed byte count, CRC result and bank ownership; ACK only after the associated writes have crossed the CDC and all required memory operations have completed. Define ordering and recovery for FIFO full, overflow, bus reset and partial transfers; never treat raw FIFO space as compressed-bank capacity.
3. **Abort boundary and independent ownership must be explicit.** Specify whether abort is legal only for RECEIVING or can cancel READY/DECODING/PENDING; if cancellation beyond receive is required, define decoder stop/drain, framebuffer-write cancellation and vblank precedence. Assert that abort/failure for token A cannot change bank B's generation, accepted metadata, read ownership, pending state, front ID or pixels, except where B independently progresses through its own valid events. Cover coincident abort/vblank, abort/decode completion, failed receive while the other bank decodes or presents, and duplicate/late abort after a new allocation. Decide whether a same-edge newly freed bank may be allocated; current decisions use start-of-edge state and may return busy.
4. **Writes and reads need a physical drain contract.** The control emits registered `mem_we`; the storage RAM consumes that strobe on the next edge. Reset gates a pending write, while abort alone does not physically erase or necessarily cancel a previously issued write. In this synchronous prototype, ownership and length limit visibility, but integration must define when all issued writes are committed or discarded before bank reuse, and prevent outstanding decoder reads or framebuffer writes from outliving ownership. `read_ready` is cleared on external `decode_done`/`decode_fail` without authenticating a generation; those events must be bound to the granted decode. Define quiesce/flush across independent resets and CDC, RAM port/collision semantics, and an explicit invalid-data rule; stale RAM contents are not zeroized.
5. **Ordering and representation need stress.** Commit order uses a 32-bit wrapping `frame_order` and signed difference; prove ordering assumptions or provide wrap-safe sequence handling. The experimental 48 KiB byte-array capacity, length/CRC and error flags need explicit oversize rejection, error attribution and credit rules. Generic inferred-memory shape is not target BRAM mapping or fit. Verify reset at each bank state, stale data after short reuse, equal-edge event conflicts, repeated sequence numbers, counter wrap, lost/duplicate ACK, and randomized independent CDC clocks with backpressure and reset.

A practical next step is a separately versioned bank-aware command/status specification, followed by assertions for token ownership, no cross-bank corruption, receive CRC/length, accepted-byte accounting, drain-before-reuse and vblank/front atomicity. Use directed simultaneous-event and restart negatives, then bounded/formal control checks and asynchronous multi-clock verification before integrating actual firmware or drawing physical performance conclusions.
