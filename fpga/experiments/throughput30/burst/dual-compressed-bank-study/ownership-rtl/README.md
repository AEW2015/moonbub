# Isolated two-bank ownership/CRC controller

`two_bank_control.sv` is a synthesizable-style **single-clock control prototype**, separate from production. It models two abstract compressed-frame slots capped at **49,152 bytes (48 KiB)** each. It exposes byte-write bank/address/data strobes; it does not instantiate a JPEG RAM, QSPI interface, CDC, decoder, pixel framebuffer or display timing. It is not integrated into a bitstream and is not a device-fit or 30 fps result.

Each slot transitions `FREE → RECEIVING → READY → DECODING → PENDING → FREE`. A single receive engine tracks ID, declared length and incremental CRC-32/ISO-HDLC; COMMIT moves a frame to READY only after the exact declared number of bytes and matching expected CRC. A single decoder is granted the oldest READY slot only while no decode or pending presentation exists. `decode_done` makes it pending; a frame ID becomes the abstract front **only on `vblank`**. A distinct receiving slot may run while another is decoding or pending. The controller retains the compressed slot until presentation, a conservative ownership choice. It does not model framebuffer data or prove pixel-level atomicity.

Zero/oversize lengths are rejected at BEGIN; busy BEGIN does not alter an existing frame. Input beyond the declared length, explicit transport-overflow, short COMMIT, wrong CRC or conflicting BEGIN/BYTE/COMMIT discards the active receive. Abort affects **only the uncommitted receiving slot**, not an independent READY/DECODING/PENDING frame; simultaneous receive-abort and pending-frame vblank is explicitly tested. It is not a command to cancel a pending or already presented frame. A simultaneous `decode_fail` and receive abort are counted independently. One operation per cycle is required; abort/overflow have priority, and conflicting byte/commit/begin is rejected. Busy/free decisions use the state at the start of the clock, so a bank freed on the same edge may be rejected until the next cycle.

The interface assumes that all commands, byte data, status and abstract memory writes are already synchronous and accepted in order. There is no backpressure input on the byte-write output, no bank ID or generation token on abort, no stale command protection, no JPEG marker validation, no byte-offset/sequence checks, no FIFO credit accounting or overflow-to-transaction attribution, no CPU/clock-domain ordering, no acknowledgement of physical memory drain, and no safely verified decode/pending abort mechanism. `decode_done`/`decode_fail` must refer to the currently granted frame; the model does not validate external decoder correctness. Upstream logic must never send stale or misrouted operations; these omissions are blockers for production integration, not implicit guarantees. Compressed-bank data is considered reusable at vblank in this model, with no outstanding external bus writes; a real memory/decoder protocol must explicitly prove that condition.

## Checks and negative controls

The complete wrapper passed with Verilator: overlapping receive/decode on different banks, CRC-valid ordered commits, rejection while both banks are occupied, pending-frame protection, exact vblank presentation, oversize/zero length, short frame, incorrect CRC, extra input byte, transport overflow, conflicting commands, independent simultaneous failures and abort/vblank on different frames. It writes and commits **all 49,152 legal bytes** in a dedicated boundary test, checking the last legal address and an independently computed CRC; 49,153 is rejected. The testbench uses abstract in-memory byte arrays, not inferred target BRAM, and continuously checks receive/decode/pending ownership invariants. It finishes with `accepted=7`, `dropped=8`, `writes=49185`, `final_front=60`.

The wrapper also constructs two local mutants without changing source: disabling CRC checking must fail the CRC rejection test, and suppressing a pending vblank presentation when an unrelated receiving frame aborts must fail the simultaneous abort/vblank test. Both fail with their specific expected messages and cannot print the pass marker. The normal and two negative logs are retained in `results/`.

An optional Yosys 0.52 generic front-end run (`read_verilog -sv; hierarchy -check; proc; opt; check; stat`) completed with `Found and reported 0 problems`; its log is retained. This is an elaboration/generic-process check, not FPGA technology mapping, full synthesis, BRAM inference, place/route, timing closure, formal proof or hardware verification. The estimated BRAM impact and existing baseline utilization are in `../baseline-resource-audit/`; no incremental utilization may be inferred from the controller alone.

Reproduce with Verilator 5.x, C++ and Python: set `BUILD_DIR` to a new empty directory and run `./run.sh`. Set `YOSYS` to an available Yosys executable to include the optional generic check; any package-specific `PYTHONPATH` is the caller's responsibility. Each simulation/mutation has a 60-second wall timeout; compiler wall time is not included.
