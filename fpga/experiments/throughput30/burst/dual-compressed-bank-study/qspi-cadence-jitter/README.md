# Dual-bank QSPI cadence with deterministic frame-arrival variation

This isolated behavioral experiment extends `../qspi-cadence10` to up to 300
unique synthetic 720×480 JPEGs. It instantiates the experimental QSPI endpoint,
CDC credit FIFO, two compressed banks, decoder, functional SDRAM and LCD scan
model. The producer samples the test-only bank-availability register at each
arrival and drops a frame immediately if neither bank is free. No frame is
silently queued by this test. It checks ordered admitted IDs, declared dropped
IDs, full simulated framebuffer and LCD canvases, and each displayed frame
against the related C decoder. The decoder model shares code with the C oracle.

Each nominal capture occurs at `epoch + floor(id * 10,000,000/3)` cycles on the
100 MHz simulation clock. Arrival variation is deterministic: offsets of
`0`, `+JITTER_CYCLES`, and `-JITTER_CYCLES` repeat in that order. For the
requested value of 200,000 cycles, this is 0, +2 and -2 ms. This tests one
periodic traffic pattern only; there is no random jitter, loss, link shaping,
ESP32 execution or actual network. The experiment assumes a complete frame is
ready at each arrival, and the test-only QSPI producer sends the frame with
credit/fence delays modeled in RTL. Presentation deadlines are measured against
nominal capture times, not the jittered arrivals. No physical input-to-photon
latency or panel timing is measured.

A verified baseline input generator is `../../longrun-study/generate-jpegs.py`;
it records input SHA-256, size, encoder configuration and Pillow version, and
requires all frames distinct. Use the same generated directory for comparison
runs. The run wrapper requires Verilator 5.x, make, C++, Python 3, and an empty
scratch build and run directory. For example, on this host the build ran inside
`radiant-xrdp` with `/home/lori` mounted at `/mnt/main_os`:

```sh
BUILD_DIR=/path/to/empty-build ./build.sh
BUILD_DIR=/path/to/build FIXTURE_DIR=/path/to/fixtures \
 RUN_DIR=/path/to/empty-run FRAMES=300 JITTER_CYCLES=200000 ./run.sh
```

Use `JITTER_CYCLES=0` for the matched baseline, and `PCLK_HALF_PS=18470` only
for the hypothetical ~60 Hz model. The default `PCLK_HALF_PS=17029` is the
existing ~65.08 Hz simulation. The optional model clock does not establish
panel support, target clock implementation, or physical validity. `FRAMES` is
1–300; watchdog and wrapper timeouts are explicit. Generated JPEGs, per-pixel
dumps and build products are local, not redistributed. `analyze.py` verifies
all fixture hashes, accounting, exact capture/arrival schedule, output/model
comparison and LCD scan records, then reports nominal capture-age percentiles,
gaps, number presented within the capture window, and busy drops.
`test_analyze.py` exercises passing accounting and rejects corrupted timing,
missing pass marker and fixture tampering. This is not a 60-second, hardware,
or end-to-end 30 fps demonstration.

## Current result

A 10-frame zero-jitter smoke run completed with 10 admitted and 10 presented,
zero busy drops or modeled underruns, 21 complete LCD scans, and 3,456,000
RGB565 pixels matching the related C model. Its capture-to-presentation age
was p50 33.23536 ms and max 38.66702 ms. All ten presentation cycles
matched the original cadence10 run exactly, and those ten input JPEG hashes
match the original fixture set. A separate ten-frame ±10 ms
periodic-jitter smoke admitted and presented all ten within the ten-frame
capture window, with zero busy drops, zero modeled underruns, and exact C
pixel checks. Its nominal capture-to-presentation age was p50 36.06722 ms
and max 46.23437 ms; retained logs and analysis are in `results/smoke-10ms`.
This is only a ten-frame synthetic stress case, not a sustainable throughput
or physical result.

Three completed 300-frame runs used the same 300 distinct synthetic JPEGs.
All presented every frame in the ten-second nominal capture window with zero
busy drops, zero modeled underruns, and 103,680,000 RGB565 pixels per run
matching the related C decoder.

The corresponding complete-canvas scan counts were 650, 650 and 599; the
final presentations were 1.06930, 1.06930 and 3.26932 ms before the ten-second
window end. The comparison is generated by `compare-runs.py` from the three
archived analyses with a matching manifest hash, and all logs and per-frame
results are in `results/`. It is one synthetic frame sequence, one deterministic
arrival-jitter pattern and one starting phase; scanout swap age is not physical
input-to-photon latency. A separate capture-phase experiment is in progress.
No 60-second, real Wi-Fi/ESP32 or physical hardware claim follows
from these ten-second model results.
