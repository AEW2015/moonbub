# ESP32-S3 emulator boot and firmware provenance

A deliberately incomplete negative-control image reached the Game Bub application’s `app_main()`; it did not reach the receiver. A separate ESP-IDF stub boot is also recorded. Espressif `esp-emu` 0.51.0 ran a locally generated, coherent IDF 5.4.3 flash set on its ESP32-S3 model. The retained `espidf-smoke.log` shows mask ROM, bootloader, factory application, CPU startup and `main_task` calling and returning from `app_main()`. The application is the `esp-idf-sys` build's `libespidf`, not the handheld. There was no FPGA, Wi-Fi, QSPI or network test; wall-clock speed is not target performance. The emulator process exited 0 after its 15-second timeout; the log, not exit status alone, is the boot evidence.

The emulator was downloaded from the official [v0.51.0 release](https://github.com/espressif/esp-emulator/releases/tag/v0.51.0). The SHA-256 of the Linux x86-64 archive matched the release API digest. No global installer or device was used. The binary and smoke flash image remain outside the repository under `/home/lori/gamebub-tools/esp-emu-study-0510`; hashes are in `SHA256SUMS.txt`. To reproduce in that directory:

```sh
timeout 30s ./esp-emu-0.51.0-x86_64-unknown-linux-gnu/esp-emu \
  --chip esp32s3 --firmware espidf-build-flash.bin --timeout 15s --net user --psram-size 0
```

The 2 MiB smoke image filled with 0xff contains the three files from the *same* `esp-idf-sys` build tree `flasher_args.json`: `bootloader/bootloader.bin` at 0, `partition_table/partition-table.bin` at 0x8000, and `libespidf.bin` at 0x10000. Their hashes, the image hash, and executable and log hashes are in `SHA256SUMS.txt`. No `--save-state` was supplied. A separate hello-world rebuild stopped before configuration because the relocated IDF Python 3.12 virtual environment lacks its interpreter; this did not affect the prebuilt stub run.

## Release image provenance and blocker

Run `python3 fpga/experiments/throughput30/burst/esp-emulator-study/check-provenance.py` from the repository. It checks the release manifest's 458 inventoried source hashes and the ELF, application binary and UF2 hashes; all 461 matched on this check. The manifest binds the exact source `bootloader.bin`, `partitions.csv`, and `espflash.toml` as well as the three application artifacts, but it records only an application update, not an assembled factory image. `firmware/build.ps1` copies the release ELF, converts it with `esptool elf2image` for 8 MB, and packages an application-only UF2. `firmware/README.md` states the updater preserves the existing bootloader and system data. Source `espflash.toml` specifies the inventoried custom bootloader, and `partitions.csv` specifies an 8 MB flash: app at 0x100000 and read-only FAT `system_data` at 0x600000, size 2 MiB.

The IDF-generated 2 MB bootloader/partition table used by the smoke test are **not** the custom 8 MB layout: their hashes and app offset differ. Do not mix them. The repository does not supply a bound system-data image; `flash_system_data.py` separately creates a FAT image from a caller-supplied directory, whose exact content and image are not recorded here. The handheld's `Device` initialization calls `mount_system_data()` with `format_if_mount_failed: false` and propagates mount errors. The configured application startup also expects other board peripherals. Consequently, no verified coherent complete flash set was found. The negative control below deliberately leaves the missing data erased and is not a complete flash set.

For the next attempt, recover or reproducibly create and document the exact intended system-data contents, generate the partition table from the inventoried CSV using the pinned ESP-IDF, retain hashes and build provenance for every component, then assemble the custom bootloader, table, application and system data at the specified offsets in a separate 8 MB image. Record whether this is a recreated test fixture or a recovered device image. Run bounded with the release ELF for symbolized diagnostics, preserving the serial log; reaching app startup will not establish receiver, Wi-Fi, FPGA or hardware functionality. Avoid putting credentials, device flash contents or binary images in this evidence directory.

## Game Bub erased-system-data negative control

Using the source and application artifacts whose hashes are bound by the release manifest, IDF 5.4.3 `gen_esp32part.py` generated the custom partition table and independently decoded it to confirm the partition offsets and sizes. A deliberately incomplete 8 MiB test image puts the 15,616-byte custom bootloader at 0, the 3,072-byte table at 0x8000, and the 2,559,856-byte release app at 0x100000; all fit without overlap. The 0x600000–0x7fffff `system_data` region, and every other unpopulated region, is explicitly 0xff. This is a constructed negative control, not a recovered device flash image or a complete runnable installation. Generated-table SHA-256 is `fd1dc4016a02d66f41f25a0ca96b856b0f5e2ef6b2c02790e973755cd460316e`; image SHA-256 is `48b93740cf2b920fe215a9e161524deb6007ac0f4151cd66e2b2d9ccddb23ee8`.

The actual release application's ELF hash prefix was reported at startup, and `main_task: Calling app_main()` appeared in `gamebub-negative.log`. TinyUSB initialization then reported assertions and `ESP_ERR_TIMEOUT`; the last observed application log was `Initializing LCD`. The 20-second emulator limit returned exit 0; this is a bounded run, not successful hardware initialization. It did not reach the system-data mount, so the expected erased-storage failure was not observed; the cause of the LCD-stage lack of further progress is not established. No network receiver, QSPI or display behavior was validated. The Game Bub bootloader itself, rather than the standard IDF bootloader, ran.

To reproduce with an installed IDF v5.4.3 and verified emulator, set `STUDY_WORK` to a new writable directory and run from the repository root:

## LCD-stage investigation

A separate 12-second run of the same negative image used emulator execution tracing with `--trace-pc-period 1000`. Its serial output is `gamebub-trace.log`; `pc-histogram.json` is a compact summary of the full local trace (SHA-256 recorded in the summary). The trace reports the `main` task running on CPU0 continuously for about 3.793 seconds at its end. Its whole-run, two-core PC histogram has 7,228 samples: 1,288 in `spi_device_polling_end`, 1,225 in `spi_hal_usr_is_done`, and 1,032 in `xTaskGetTickCount`. The histogram is aggregated across tasks and the complete run, not a call stack or exact attribution to the LCD. It supports a **SPI transaction-completion polling** hypothesis; it does not conclusively establish the exact blocking instruction, peripheral root cause, or whether an LCD slave response would resolve it.

Rev4 enables ILI9806E. After the last serial message, `Device` sets up SPI3 and the LCD, then calls `gamma::initialize`, which invokes the panel's `init()`. That function toggles reset, sleeps briefly and transmits packed nine-bit commands via `self.spi.write`. There is no LCD status input or explicit panel-response polling in this path. Thus a missing LCD GPIO response is not supported by the source as an explanation. The emulator documentation lists GP-SPI generally, but the v0.51.0 native CLI does not document an attachable generic SPI slave or GPIO-response injection; its host control channel lists reset, eFuse and flash operations. GDB memory/register control is documented, but changing those would be an artificial fault injection and was not performed. A standalone matching-SPI3 probe would be useful after repairing the isolated IDF build environment; it should test the real transaction setup and SPI completion before any proposed emulated peripheral adapter. No such probe or hardware behavior is claimed here.

Reproduce the diagnostic with the previous negative fixture command, replacing the timeout with `--timeout 12s` and adding `--trace "$STUDY_WORK/trace.json" --trace-pc-period 1000`. Sample counts and times vary with execution and this is not a target timing measurement.

## Isolated SPI3 polling probes

A separate Python 3.12.16 runtime and virtual environment were installed locally using uv 0.13.7; ESP-IDF 5.4.3 dependencies were installed under its `espidf.constraints.v5.4.txt`. No global configuration or release firmware changed. The environment used the already installed IDF v5.4.3, Xtensa GCC 14.2.0, CMake 3.30.2 and Ninja 1.12.1. `python-packages.txt` records the resolved Python packages. The portable `spi3-probe` source configures SPI3 at 5 MHz, half duplex, DMA auto, MOSI GPIO10, clock GPIO11, software CS GPIO12 and reset GPIO13, then polls one 7-byte write encoding the first ILI9806E command. It approximates the release's setup using ESP-IDF C, not the Rust device wrapper or the whole LCD init. `probe-nodma.c.txt` differs only by selecting `SPI_DMA_DISABLED`.

Both images booted in esp-emu 0.51.0, printed `PROBE_BEFORE_SPI3_POLLING`, and did not print the immediately following `PROBE_AFTER_SPI3_POLLING` during their 10-second emulator limits. `spi3-dma.log` and `spi3-nodma.log` preserve both logs. The process exit 0 reflects timeout, not transaction completion. This independently reproduces noncompletion for these two SPI3 configurations in this emulator, consistent with the release trace's SPI polling samples. It does not establish why the emulated transaction fails, the release's exact call stack, target hardware behavior, or any networking/QSPI functionality.

To build the DMA case with a correctly exported IDF 5.4.3 environment, copy `spi3-probe` to an isolated writable directory, then run `idf.py set-target esp32s3`, `idf.py build`, and `idf.py merge-bin`. For the non-DMA case use a separate copy and replace `main/probe.c` with `main/probe-nodma.c.txt` before building. Run each generated merged image with `timeout 25s "$ESP_EMU" --chip esp32s3 --firmware "$IMAGE" --elf "$ELF" --timeout 10s --net user --psram-size 0`. Build timestamps and tool versions may alter artifact hashes; recorded hashes identify the tested images, not a guarantee of bit-for-bit reproducible builds. Captured artifact hashes follow in `SHA256SUMS.txt`.

## Emulator-only LCD bypass

A separate copied firmware source tree applied `lcd-bypass.patch`, replacing only the ILI9806E command's actual SPI write with `Ok(())`. This suppresses **all** LCD command writes and is an artificial test harness, not the release, hardware behavior or an operational display. Rev4 SPI2 already services the FPGA, so assigning SPI3's LCD directly to SPI2 would require shared-bus arbitration and rerouting; it is not a drop-in replacement. The source copy was built with Cargo `+esp193 build --locked --release --features rev4 -j 2`, ESP-IDF 5.4.3, in a new disposable `gamebub-esp32-dev:24.04` container. The original toolchain and IDF tree were mounted read-only; Cargo target, package cache, and writable ESP-IDF Python environment were confined to the separate copied workspace. The host build first failed because `cc` was missing, and the first container build failed because the IDF Python environment was read-only. A copied writable Python environment allowed the successful build. `lcd-bypass-build-tail.log` records the final result and its expected unused-SPI warning.

The test-only ELF and application hashes are respectively `18fc68552a1c4a8bdd6e79ec212f79383c2e3915e4832ec0b79cc4ba5ba1e71a` and `65c2cdf40947eb020176155e7442245039170fa23c6d219bad09b63932e43f1f`. `esptool --chip esp32s3 elf2image --flash_mode dio --flash_freq 80m --flash_size 8MB` produced the app. An isolated 8 MiB negative image used the same verified custom bootloader and generated partition table described above, the test-only app at 0x100000, and erased `system_data`; its SHA-256 is `dddd62e6cb61fbddb801e5c5975c75fad420d09c9811b636ffced0e7a2af0141`. With esp-emu 0.51.0 and the same 20-second bounded command as the negative control, `lcd-bypass-boot.log` records the application passing the previous LCD-stage stall, then a fuel-gauge configuration warning and `Error: IMU init` caused by an `i2c error`, after which `app_main()` returned. TinyUSB initialization still failed. This establishes progress to a later missing/unhandled I2C interaction in this modified test image, not successful device initialization, an observed `system_data` mount, an actual receiver run, or a production fix. The exact reason for the I2C error requires separate testing.

## Assessment: bypassing FPGA programming

The `MainMenu` startup path calls `program_boot`, enables an FPGA button interrupt and sets panel control before constructing `UI`. Suppressing that call alone could test whether some CPU-side UI initialization is entered, but would not exercise a real display or prove useful receiver behavior. `UI::new` immediately writes FPGA registers, changes display mode, schedules further FPGA writes and sends rendered lines through the FPGA; an unattached SPI slave cannot validate these interactions. The earlier SPI2 smoke only established transfer completion, not register semantics.

The receiver is not started merely by constructing the main menu: a UI connect callback calls `streaming::connect`, whose worker reads `/sdcard/moonshine.cfg`, configures Wi-Fi, checks or loads `/sdcard/moonshine.bit`, verifies the MSV1 magic/version and control state, and only then binds UDP 5533. In the current fixture SD mounting fails, no control input or FPGA slave is implemented, and the empty synthetic system partition has no boot bitstream. Simply returning success from FPGA programming and status checks would bypass the very contracts needed to interpret an end-to-end result. Consequently no additional programming bypass or fabricated identity was applied for this assessment.

A useful next isolated experiment would define a labeled functional FPGA register/stream model (including identity, advertised remaining bytes, begin/commit/abort and errors), a deterministic host-side connect trigger and an explicitly synthetic local config using non-personal credentials for the emulator's built-in AP. Retain the real Rust worker, UDP socket and `protocol::Receiver`, inject controlled packets, and check emitted transactions and feedback against independent expected traces, including loss and abort. Independently verify that the emulator can attach the required SPI peripheral or use a documented test-only transport seam; if the latter, label that SPI, DMA, GPIO timing and physical FPGA are bypassed. Test the real FPGA RTL separately against the same transactions and preserve the distinction. This requires new fixture engineering and cannot be inferred from a silent UI loop.

## MSV1 receiver on the emulated target CPU

An isolated Rust test executable compiles the repository's **unchanged** `firmware/handheld/src/streaming/protocol.rs` (SHA-256 `32a91ffaf0b39a82f11036be7e501765cd3f9fed6905c27b6efc01f358d79e64`) with `msv1-target/main.rs` replacing the application entry point in a separate source copy. Rust esp193 and ESP-IDF 5.4.3 produced an ESP32-S3 target ELF. On esp-emu 0.51.0, `msv1-target/fixture-trace-boot.log` records explicit success markers for a valid two-chunk frame, corrupt CRC rejection and subsequent recovery, malformed/truncated headers, and a duplicate rejection. A first attempt using Rust `println!` produced no visible markers despite returning from `app_main`; it is retained separately and is not counted as a pass. The later harness uses the IDF logger.

The same harness also replays 26 datagrams for frame zero of the existing synthetic `network-rtl-study` clean trace. `msv1-target/make-trace.py` regenerates them using the repository Python packetizer and fixture JPEG, checks every datagram SHA-256 against the recorded clean trace in order, and checks 26,159 source bytes and independently computed host zlib CRC32 `eceeb9c5`. Its length-prefixed byte stream hashes to `a8ff3d87e165247637d97fd2b56414f54943337ff7cb11102aa73cba26f26e05`. The emulated Rust Receiver accepted all packets; a synthetic streaming sink checked ordered frame offsets, 26 packets, one completion, 26,159 bytes and CRC32 `eceeb9c5`. The sink uses the same Rust CRC function as the receiver; the host zlib check supplies the independent expected CRC. The log's `MSV1_TARGET_PROBE_PASS` is the success marker; timeout exit status is not.

This executes the protocol module and harness on an **emulated** target CPU; it is not the production application, a real UDP or QSPI path, Wi-Fi/FPGA test, real hardware or performance measurement. The packet timestamps are not replayed, and the sink records/validates bytes in-process rather than forwarding them to a device. Fixture and generated binary remain outside the repository.

To reproduce, copy `firmware/handheld` to a new workspace, replace only its `src/main.rs` with `msv1-target/main.rs`, and generate its `src/fixture.trace` using `python3 msv1-target/make-trace.py PATH_TO_0000.jpg PATH_TO_COPY/src/fixture.trace`. ## Three-frame corruption and recovery on the emulated target

The extended `msv1-target/recovery-main.rs` replays the first three distinct synthetic JPEG fixtures through the unchanged Rust receiver. `make-recovery-trace.py` verifies each fixture against the clean network-study manifest, checks independent zlib CRCs and validates every one of the 79 original clean-trace datagram hashes before packing them. The clean input blob is SHA-256 `bef1ac9f645d0378849d4e3b0d6b4d7c935e309338a41c6a067891596405d372`. In the target harness only, the final payload byte of frame 1 is flipped after unpacking; the original recorded input is unmodified.

The bounded emulator log `msv1-target/recovery-boot.log` shows frame 0 committed with 26,159 bytes and CRC `eceeb9c5`; the altered final packet of frame 1 was rejected with `Integrity`, and the synthetic sink discarded its 25,600 previously accepted bytes; frame 2 then committed with 26,991 bytes and CRC `1ea3e1d5`. Totals were 79 input datagrams, two committed frames and one rejected frame. The sink checks order and updates a streaming CRC, but does not retain or transmit the bytes; it shares the receiver's CRC routine, with host zlib supplying independent expected CRCs. These are synthetic JPEGs and a deliberate deterministic corruption, not captured user content or a real network loss. The test runs only in an emulated CPU harness and does not establish UDP, FPGA, QSPI, Wi-Fi, target hardware or performance behavior.
