# Experimental narrower X-stage multipliers

The X-stage inputs are signed 16-bit values. The isolated candidate narrows four multiplier data operands from 32 to 16 bits, the fifth (a sum/difference of two input values) from 32 to 17 bits, and the positive cosine coefficient operands from 32 to signed 13 bits. Products and downstream state retain their original widths. The source change is confined to this test candidate, not integrated production RTL. The Y stage is **not** changed: its input width/overflow behavior needs separate analysis.

With Yosys 0.52, intermediate generic `synth_xilinx -family xc7 -run begin:coarse` mapping produced **16 DSP48E1 cells for the original X module and 9 for the candidate** with default parameters; both report the same `block_out` memory-to-register warning. These are intermediate standalone mappings, not actual target-device LUT/DSP utilization, timing, power, a full-JPEG design total, or proof of speedup. The full Yowasp synthesis attempt for the original stopped logging at ABC despite a zero launcher exit, so no complete mapping or implementation result is claimed.

Verilator 5.020 and Vivado 2025.2 XSim each compared the two stage implementations cycle-by-cycle over **100,000 deterministic pseudorandom cycles**, including arbitrary 16-bit values, controls, resets and injected extreme values, with no observed mismatch. These are tests, not by themselves a formal proof. A subsequent [compositional proof](../narrow-x-proof/README.md) independently checks unbounded two-state sequential equivalence after synchronous reset for the default parameters. A separate 10-step unconstrained-input bounded SAT attempt with reset and zero initial state was **inconclusive**, reaching 1,297,234 variables and 3,786,918 clauses before the 300-second timeout. It is not a proof. `formal_miter.v` records that attempt; no formal pass is claimed.

The candidate also replaced only the original X stage in the full experimental QSPI/JPEG/memory/LCD behavioral bench for two independent one-frame runs: one synthetic JPEG and one precompressed gameplay-derived JPEG. Both passed 345,600 exact C-model framebuffer pixels and 345,600 ordered modeled LCD scanout pixels without detected underruns (`synthetic-pipeline.log`, `game-pipeline.log`). The C model shares decoder algorithms with the original RTL. Two images and randomized stage inputs cannot cover all JPEGs or replace a broad decoder corpus, target synthesis, clock/CDC analysis and hardware measurements. The adjacent compositional proof covers the X-stage sequential logic under its stated assumptions, not the entire decoder.

Run `run-stage.sh` with Yosys and Verilator in PATH and `BUILD_DIR` set to an empty directory to reproduce coarse mapping and the randomized comparison. Run `run-pipeline.sh` for the synthetic full-path test; set `FIXTURE_DIR` to a compatible **single-frame** fixture to test another image. The original source and C model are not modified. XSim was run separately via the Vivado MCP flow using a generic installed part and the same testbench; it did not use the target FPGA part or establish implementation timing.

A separate, exhaustive **combinational arithmetic** SAT check passed in Yosys 0.52: for every pair of signed 16-bit operands and every nonnegative coefficient from 0 through 4095, the narrowed products equal the original 32-bit expressions for the direct, sum and difference cases. This coefficient range includes all seven X-stage cosine constants. `formal_mul.v` and `run-formal.sh` reproduce the check, with a 300-second timeout and explicit success-marker verification. This proves only those arithmetic identities; it does **not** prove that the full registered stage, its controls, reset behavior or a whole JPEG decoder are sequentially equivalent. The separate ten-step full-stage attempt remains inconclusive.

A 90-frame game-derived workload was also run with the candidate X stage and the unchanged Y stage through the multi-frame QSPI-to-LCD scoreboard. All 90 RGB565 framebuffer dumps and presentation cycles exactly matched the original-stage run, and **194 complete modeled LCD canvas scans** covered all 90 IDs without detected tearing or underruns. `run-multiframe.sh` reproduces this with a compatible 90-frame fixture directory; the input manifest is in `../../gameplay-study/manifest-90-near30.json` and the source video is not redistributed. The wrapper was rerun successfully; the recorded logs are `multiframe-simulation.log` and `multiframe-verified.jsonl`. This remains a short functional simulation, not a target-device timing or fit result.
