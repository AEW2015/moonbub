# Scheduled emulator/RTL bridge: feasibility and smallest next test

The present live integration is a **functional** stop-and-wait bridge. The Verilator DPI function blocks inside a TCP receive while the guest/adapter wait for an ACK; RTL simulation time does not advance during that wait. There is no authoritative clock shared with esp-emu. Consequently neither wall time nor RTL cycle differences bound real end-to-end latency or 30 fps. The emulated guest also embeds fixtures as test oracles, uses a synthetic network/IPC sink and does not execute the production frame worker or actual QSPI DMA.

## What exists and what is missing

Local esp-emu 0.51.0 `--help` advertises a GDB stub, single instruction stepping, a control channel for reset/flash operations, and optional task/PC tracing. Its documented CLI control commands do **not** expose an externally advanced, synchronized virtual-time or pause-until-timestamp API. This is an observation about the local CLI, not proof that the emulator's internals cannot support one. GDB stepping alone does not establish how emulated peripherals, network, RTOS timers or DMA advance, nor an accurate mapping from S3 execution to physical elapsed cycles. Verilator's `--timing` advances the RTL's clock and modeled peripherals independently; the existing DPI socket cannot by itself synchronize either process. Host UDP/TCP service and emulator boot introduce scheduler and I/O effects that must not become implicit simulated radio/CPU time.

A true live virtual-time co-simulation would need (1) a verified emulator API or instrumentation with an authoritative monotonic guest time and deterministic pause/advance semantics for CPU **and** modeled peripherals/network; (2) an orchestrator that advances both engines to the minimum next event on one shared epoch, handles ties and avoids deadlocks while ACKs/credits are pending; (3) bounded ingress, receiver, QSPI and display queues with explicit ownership, service, credit, timeout, overflow and cancellation rules; and (4) a defined mapping from emulated or calibrated instructions/peripherals to physical time. None of that follows from the successful 84-event functional trace. The existing emulator's test network layer and substituted sink are not a calibrated radio or physical QSPI model. No speed claim is sound until those assumptions are explicit and validated.

## Minimal useful next test: scheduled offline handoff

Do not label the following a synchronized live co-simulation. Use it to connect and stress already verified components under **declared model times**:

1. Capture an ordered, hash-verified guest BEGIN/DATA/COMMIT/ABORT event stream and packet/frame IDs from a clean three-frame functional emulator run. Record guest timer readings and wall time only as diagnostics, with their provenance. Keep the existing guest byte/CRC/event audit; its embedding of the fixture remains a test oracle. Establish separately whether guest timer readings advance deterministically under repeats and socket waits before using any as scheduling input. If not, do not use them as CPU service measurements.
2. Assign capture/packet arrival times from a fixed **synthetic** 8 Mbps L3 serialization/jitter trace at nominal frame times 0, 33.333…, and 66.666… ms. Replay actual captured payload bytes into Verilator through a **nonblocking**, bounded event FIFO and the real experimental QSPI credit logic. RTL must continue clocking while the FIFO is empty; an offline scheduler injects arrivals at their declared RTL cycles and accounts for bytes held while the sink is busy. No full-frame stimulus/preload may masquerade as bounded transport storage. Start with a five-event queue and explicit `drop whole frame + confirmed pre-commit abort` on overflow; log every arrival, enqueue, service start/end, credit wait, drop, commit and front-buffer boundary. Confirm partial frames never publish and preserve the prior front.
3. Treat guest processing and transport service as explicit parameters, not measured facts: an optimistic zero-service control and declared per-packet service delay examples (e.g. 0.2 and 1 ms) plus 0/1/5 ms artificial network stalls. Apply them to availability timestamps before injection; do not double-count a delay already present in a trace. Run each case with deterministic seed, fixed simulated-time and wall-clock watchdogs, byte-exact C-model checks for each published frame, and full ID accounting. Test one no-stall three-frame trace and one controlled stall that provably fills the bounded FIFO, with a no-fault control.
4. Report schedule assumptions, input frame IDs, complete/dropped IDs, queue bytes/high-water, CRC/abort outcomes, capture-to-modeled-publication age and per-stage waits. A passing result can establish correctness, conservation and the consequences of these **assumptions** for that finite trace. It cannot establish physical ESP32 CPU time, radio goodput or display performance. Extend the workload and calibrate only after instrumentation is checked against board timer traces, real link/packet traces, QSPI logic-analyzer/ILA captures, and actual FPGA timing/SDRAM behavior.

For a later **live** experiment, first prototype an emulator clock API or instrumented guest handshake and demonstrate monotonic reproducibility, paused-time behavior, per-event deadlines, and forward progress with both ends held at barriers. Only then use a shared-time scheduler and bounded queues. Explicitly test late/duplicate/reordered packets, missing SOF/EOF, queue full, busy begin, lost/ambiguous abort and abort-vblank races. Keep wall-clock watchdogs and any simulated deadline separate; a watchdog terminating a slow simulator must not be reported as a modeled network timeout.
