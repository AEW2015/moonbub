# Emulator-to-QSPI RTL live bridge

This isolated experiment connects an ESP32-S3 emulated research guest and host adapter to a live Verilator model. The guest receives MSV1 datagrams, applies the unmodified Rust receiver, and sends begin/data/commit events; the adapter validates each event against the expected packet trace and relays **actual payload bytes** to this RTL-side socket. The testbench does not preload a JPEG. The research guest does embed the fixture as a validation oracle; DATA bytes sent to RTL still come from its received datagrams, so this does not demonstrate a production guest memory footprint. It sends each accepted DATA body incrementally over the experimental `cdc-credit` QSPI endpoint, requires contiguous offsets and CRC agreement, commits, and waits for the RTL decoder and modeled display to publish. It checks every framebuffer location against decoder output; the host wrapper additionally compares the presented frame against the related C JPEG model.

The stream protocol is TCP on loopback, default `127.0.0.1:15534` (`BRIDGE_HOST` and `BRIDGE_PORT` are adjustable for isolated tests). Every event is a four-byte big-endian body length followed by type byte, sequence u32 and frame ID u32. `B` additionally has total length and CRC u32; `D` has offset u32, length u16, and 1–1,024 actual bytes; `C` and `A` have no additional fields. All integers are big endian. The body is limited to **1,039 bytes**, one event is in flight, initial sequence is zero and subsequent sequences increment by one. The five-byte ACK is status byte plus sequence u32. DATA ACK follows QSPI transfer; COMMIT ACK follows RTL presentation. Socket reads and writes have 15-second wall timeouts. Invalid framing, sequence, offsets, length, ID, CRC, failed QSPI or EOF abort the simulator; no malformed frame is allowed to carry a success marker.

Simulation time is frozen while the blocking DPI call waits for an event. The adapter deliberately waits for ACK before the guest sends the next packet; CPU and simulated RTL do not advance on a shared clock. Consequently simulated cycles, socket speed, throughput and wall time are **not end-to-end latency, throughput, or 30 fps measurements**. The guest uses the emulator's substituted test network path, not the physical ESP32 Wi-Fi/firmware/QSPI/DMA path. There is no production firmware, actual FPGA, SDRAM timing signoff or real network in this test. The separate C JPEG model shares decoder algorithms and is not an independent reference.

## Evidence and reproduction

A clean cross-agent wrapper run transferred one frame: 28 sequential events (BEGIN, 26 DATA, COMMIT), 26,159 compressed bytes, and 345,600 / 345,600 exact RGB565 pixels. The guest, adapter, RTL, and model-comparison checks each exited successfully. Small exact logs, event hashes and comparison are retained in `results/clean-live/`; the live wrapper's ELF, flash and binary hashes are in `sha256.json`. The RTL build inputs used in that run match the 33 staged source files listed in `results/rtl-source-sha256-initial.txt`. The source hashes and experimental status of the emulator path are recorded in `../esp-emulator-study/live-bridge/`; see that directory's `run.py` for the complete host orchestration.

`build.sh` compiles the RTL and DPI sources into a new empty `BUILD_DIR` with Verilator 5.x and a C++ toolchain. `test_socket_controls.sh` uses a separate loopback mock sender to check bad initial sequence, immediate disconnect, oversized body and truncated body. It requires `RTL_BINARY`, `FIXTURE_JPEG`, `OUTPUT_DIR` and optionally a free `BRIDGE_PORT`; each test has a 60-second RTL wall timeout, waits for the sender to exit with a bounded cleanup, requires the specific failure, and rejects any success marker. These are host protocol controls, not emulated-guest or RTL image tests. The recorded controls are under `results/`.

The data events are backed by a maximum 1,039-byte socket buffer and QSPI chunks obey the experimental FIFO credit response. The simulation testbench still allocates model framebuffer and SDRAM state; it does not prove memory sizing, scheduling or electrical timing on an ESP32 or FPGA. No multi-frame, packet-loss, retransmission, recovery or sustained-rate claim follows from one clean frame. Port binding should remain loopback on a trusted machine; the diagnostic protocol is unauthenticated.

## Live final-datagram corruption and abort

A separate emulated guest receives a deliberately corrupted final MSV1 datagram. Its unmodified Rust receiver reports integrity failure before emitting that packet as DATA. The guest sends `A` instead of COMMIT after **25 accepted DATA events / 25,600 bytes**; the adapter and RTL verify sequence and acknowledge it. With the explicit testbench-only `+FINISH_AFTER_ABORT=1` option, the RTL waits through two LCD frame boundaries and checks no completed, decoded or presented frame, no front-valid, decoded pixels or framebuffer writes, then acknowledges abort and exits normally. The guest, adapter and RTL all exited successfully; source and clean wrapper are `../esp-emulator-study/live-bridge/{guest-abort.rs,adapter-abort.py,run-abort.py,check-abort.py}`. All event hashes and logs are in `results/final-abort/`.

The same updated RTL binary also passed a fresh positive emulated-guest wrapper with 26 DATA events / 26,159 bytes and **345,600 exact C-model pixel matches**; its logs are in `results/final-positive/`. Both wrappers record matching RTL binary hashes in their `sha256.json`. The 33 exact Verilator/DPI source hashes for this updated build are in `results/rtl-source-sha256-current.txt`; `rtl-source-sha256-initial.txt` refers to the earlier clean run. Four protocol failure controls were rerun against the updated binary and passed their expected nonzero-error checks. Their failures are deliberate testbench shutdowns, not clean target aborts.

The corruption control uses an emulated guest and idealized loopback adapter; simulated time freezes at each socket exchange. It starts with no prior valid displayed frame and sends abort during receive, not decode or pending presentation. It does not cover lost or ambiguous abort, timeout, a late packet, clock-domain races, or a real device. This is a controlled functional integration check, not proof of production safety or performance.
