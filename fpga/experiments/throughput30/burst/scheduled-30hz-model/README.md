# Three-frame 30 Hz source-schedule feasibility model

This is a **Python discrete-event model**, not the offline RTL replay, a running emulator or live co-simulation. It reads the 84 actual guest-emitted, hash-audited event bodies captured by `../scheduled-live-replay/`; it verifies the capture and each event hash. The frame payloads and recorded guest ABORT are authentic to that earlier synthetic emulator run, but their original stop-and-wait emission times are **not** used as real execution timing.

A new hypothetical producer assigns frame BEGINs at exact rational 30 Hz: 0, 33.33333 and 66.66666 ms. Each frame's first DATA is assigned 1 ms after BEGIN, subsequent DATA events are spaced 1.2 ms apart, and COMMIT/ABORT is one interval after its last DATA. The producer emits the captured bodies independently of any modeled sink ACK. This is a newly defined synthetic producer, **not** the existing stop-and-wait guest. It does not simulate CPU, real encoder, real Wi-Fi or ACK handling. The guest had previously validated fixture bodies and rejected frame 1's corrupt final datagram; this model replays the resulting ABORT event and does not re-execute that guest or its CRC decision.

The sink model has five event slots and a 5,195-byte body budget, including the in-service event. It assumes 200 µs/KiB of DATA service and 20 µs for BEGIN, COMMIT or ABORT; these are explicit model parameters, not target measurements. Upon BEGIN while a prior frame is still being received or pending presentation, it drops the new whole frame and ignores its remaining events; it does **not** abort the previous pending frame. A full FIFO drops the affected whole frame and clears its queued events, with an instantaneous modeled abort if needed. These are hypothetical policies, not production behavior or a proven safe RTL implementation. The model enforces ordered DATA offsets and verifies captured length and CRC at each modeled COMMIT; incomplete/corrupt data cannot commit. CPU time, memory allocation, actual FIFO/CDC backpressure, abort acknowledgement, LCD phase, UART/USB, audio, network overhead/retries and reordering are excluded.

## Finite results

| Modeled post-commit release | Presented | Dropped | Peak event FIFO | Capture-to-modeled-release age |
| --- | --- | --- | ---: | --- |
| Fixed 33.97969 ms | 0, 2 | 1: BEGIN while prior frame pending | 1,039 B, 1 slot | frame 0: 66.19969 ms; frame 2: 67.39969 ms |
| Zero-release control | 0, 2 | 1: recorded guest ABORT | 1,039 B, 1 slot | frame 0: 32.22000 ms; frame 2: 33.42000 ms |

The fixed value is the **largest commit-to-presentation interval observed in one earlier ten-frame RTL trace**, reused as a constant hypothetical service time. It is not an upper bound on real hardware or even other RTL phases. The zero-release case is an unrealistic control to show the effect of the busy policy. The first case preserves frame 0's pending presentation when it drops frame 1; it does not reach the recorded ABORT for frame 1, because it discards that frame's later events. In the control, frame 1 is accepted and its recorded guest ABORT is consumed. The two presented frames' CRCs match the captured BEGIN metadata in both cases. These ages are model outputs measured from assigned BEGIN times, **not** input-to-photon measurements.

There is an important extension boundary: under the stated spacing, frame 2's COMMIT is assigned **100.06666 ms**, but a fourth 30 Hz BEGIN would be due at **100.00000 ms**. The recorded stop-and-wait event order therefore cannot simply be concatenated forever at 30 Hz without defining whether a producer interleaves frames, queues capture, changes packet/service rates, or drops/replaces frames. This three-frame sample has no fourth frame, so it does not answer that question or prove 30 fps.

`results.json` retains every modeled event action and frame result. `OUTPUT=/tmp/repro.json ./run.sh` runs five directed tests (busy-BEGIN prior preservation, the zero-release ABORT control, whole-frame queue overflow, CRC corruption rejection and the fourth-frame overlap), then regenerates the results; a rerun was byte-identical. A deliberate slow-service stress control in the tests forces the modeled 5-slot queue full and drops all three frames; it is not a hardware result.

For an RTL extension, first define how new SOFs interact with pending frames and partial buffers, how source timing and interleaving work after the third capture, how the actual receiver's CRC/ABORT decisions map to the sink, and how bounded queue overflow, stale-frame handling, timeouts and credited QSPI transfers are acknowledged. Then use scheduled guest-emitted bytes with explicit queues and compare every completed output, including a prior-front preservation case. A physical performance claim additionally requires real guest scheduling, memory/transport behavior, measured radio traces, hardware QSPI/FPGA timing and display observations.
