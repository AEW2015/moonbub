# Offline scheduled replay of emulator-produced data

This isolated experiment first **records actual event bodies emitted by the emulated ESP32-S3 research guest** in the three-frame live bridge. The recording adapter writes each received body before relaying it; its existing event audit records SHA-256 only after the matching RTL ACK. `data/guest-events.bin` contains 84 length-prefixed events, including the DATA bytes; `data/adapter-events.jsonl` contains the corresponding audit. The whole capture has SHA-256 `7853a8233831ff6ceb6e44fe067ea32225a76df565647e56be45b72199fc8a0d`. `prepare_schedule.py` verifies the capture hash, every length, sequence and event hash before using these actual bytes. A fresh `capture.sh` rerun produced the exact same bytes. The data is synthetic fixture content; no user video is recorded.

The recorded sequence has valid frames 0 and 2 and a partial frame 1 followed by the guest's ABORT after it rejected a corrupted final datagram. See `../live-multiframe-bridge/README.md` for the separate emulator/live integration. The guest embeds fixture bytes as a validation oracle; the RTL replay **does not preload JPEG payloads**. The source payloads are the recorded guest DATA bodies, not bytes reconstructed from the fixtures.

## Replay and assumptions

`prepare_schedule.py` assigns **new synthetic event availability times**: frame BEGINs are 90 ms apart, the first DATA is 1 ms after BEGIN and subsequent DATA bodies are 1.2 ms apart, with COMMIT/ABORT one interval after the last DATA. These times do not come from esp-emu or a real network. The frame spacing is deliberately relaxed to avoid treating this as a 30 fps test. Host processing, CRC computation and disk reading have no modeled latency; QSPI and the experimental FIFO, decoder, memory and LCD run on the RTL clock. An optional 10 ms artificial consumer stall occurs immediately before servicing frame 0's second DATA. This is a scenario input, not an observed CPU or Wi-Fi stall.

The DPI file reader holds at most one **1,039-byte lookahead event**. When its scheduled time arrives the producer copies its actual bytes into a five-slot RTL event FIFO, each slot at most 1,039 bytes, a 5,195-byte modeled FIFO budget. Thus the event body storage bound is at most **6,234 bytes including lookahead**, excluding framebuffer/SDRAM model, queue metadata and host/runtime storage. The in-service event remains charged to the FIFO. The FIFO holds the event body, which has a 15-byte DATA event header; this is not a measured ESP32 socket-buffer footprint. The testbench records all 84 arrival cycles/actions and FIFO occupancies, DATA service/forward cycles, drops and presentations. The RTL clock continues while the queue is empty; there is no live emulator process or shared-time co-simulation during replay.

On FIFO overflow, this finite test's policy marks frame 0 discarded, suppresses its remaining recorded events, aborts the active pre-commit RTL receive, and verifies no new completion, decode, publication or framebuffer writes. It asserts all events flushed from the queue belong to that frame. It does **not** implement or claim a general multi-frame overflow policy; overflow on any other frame or event stops the test. Frame 1's ABORT is the actual recorded guest decision, not an independently re-executed guest CRC calculation in the offline replay. Idle CPU scheduling, late/reordered/duplicate events, missing abort delivery and actual ESP32 timing are not modeled.

## Results

| Case | Presented IDs | Dropped IDs | Peak FIFO body bytes | Related C-model checks |
| --- | --- | --- | ---: | --- |
| No artificial stall | 0, 2 | 1: guest ABORT | 1,039 | frames 0 and 2: 345,600 exact RGB565 pixels each |
| 10 ms consumer stall | 2 | 0: FIFO overflow; 1: guest ABORT | 5,195 | frame 2: 345,600 exact RGB565 pixels |

In the overflow run, frame 0 had already forwarded 1,024 bytes before the queue filled; the testbench aborted it without commit and recovered to frame 2. In the no-stall case, frame 0's prior front was preserved through frame 1's abort and through recovery. In the overflow case there was no prior valid front at frame 1's abort, so that case does not test prior-front preservation. `results/no-stall/run.log` and `results/stall/run.log` include all 84 arrival actions. The recorded comparisons are related to the RTL JPEG algorithms and are not independent decoders.

The reproducible wrapper passed both cases (exit 0) and checked every arrival's exact assigned timestamp and frame ID, queue bounds, presentation/drop IDs and overflow location, then ran the three exact C-model comparisons. Each Verilator run has a 400-second wall timeout; a separate 1-second modeled RTL watchdog is present. Full generated output is `/home/lori/gamebub-tools/scheduled-live-wrapper-v3`; the wrapper log is `/home/lori/gamebub-tools/scheduled-live-wrapper-v3.log`. These finite, artificially scheduled results are **not** a synchronized guest/RTL timing result, a physical performance measurement or proof of sustained 30 fps. The known original-core simultaneous abort/vblank failure described in `../abort-study/` is not exercised.

## Reproduce

1. `data/` retains the 84 original guest-emitted event bodies and their audit. To recapture, set `GUEST_INPUT_DIR` to a directory containing the validated multi-frame `guest.elf`, `guest-flash.bin`, and `fixture.trace`; set `ESP_EMU` to esp-emu 0.51.0, `RTL_BINARY` to the built `Vtb_live_multiframe`, and `OUTPUT_DIR` to a nonexistent directory, then run `./capture.sh`. It uses loopback ports 15533 and 15536, bounds/cleans up processes, verifies markers and per-event hashes, and prints the capture SHA. `data/provenance-sha256.json` identifies the original guest ELF/flash, trace, emulator, RTL binary and recorder. The live adapter's functional limitations still apply.
2. Complete `../network-rtl-study/run.sh` and retain its build directory with fixtures and related C model. Set `BASE_BUILD_DIR` to that directory, `BUILD_DIR` to a new empty directory, and run `./run.sh` with Verilator 5.x, a C++ compiler, Python and Pillow available. It regenerates the schedule, builds the replay, runs both bounded scenarios and checks the exact outputs. `results/rtl-source-sha256.txt` records and verifies the 33 staged RTL/DPI build inputs; `results/schedule-sha256.txt` identifies the generated schedule.
