# Packet-streaming replay feasibility check

This is a preliminary storage/timing calculation using the actual MSV1 packet trace and instrumented RTL timing from the neighboring experiments. It is **not** a streaming-packet-to-RTL run, a cycle-accurate queue model, an ESP32 execution or a measured Wi-Fi result. No hardware or production firmware changes are made.

## What the code supports

The MSV1 SOF header already contains the whole frame's length, dimensions and expected CRC. Production `Receiver::accept` requires contiguous offsets and validates the final CRC before accepting EOF; production `session` starts the FPGA on accepted SOF, forwards each accepted payload, and sends commit only after EOF succeeds. Thus full-frame storage on the ESP32 is not required by the protocol. The decoder core, however, waits until commit before decoding and will not accept another begin until decode, drain and pending presentation are all finished.

The separate 4+1-slot `Window` is a research adapter, **not** integrated production code. Its busy and error handling in the mock may abort a previous pending frame, so it must not be treated as a transparent queue in front of the real FPGA. Production `forward` checks remaining compressed-byte capacity, not the experimental QSPI endpoint's CDC FIFO credits. A packet-level RTL harness must implement and check the latter explicitly, while preserving CRC, packet order, partial-frame abort and actual busy semantics. It also needs an explicit action on a full queue and on a lost SOF/EOF. None of these is supplied by the full-frame staging bench.

## A concrete pressure case

`analyze.py` reconstructs the first two JPEGs' actual MSV1 datagrams, verifies every datagram hash against the retained 8 Mbps no-loss trace, and checks their reference outcomes. It uses the shortest **observed** commit-to-decode-ready time among the ten prior baseline frames as a conditional estimate; it is not a guaranteed lower bound. Under deliberately optimistic assumptions—instantaneous forwarding and CRC, frame 0 committed exactly on its last packet arrival, and no display-boundary wait—frame 1's SOF still arrives while frame 0 is decoding. Before this hypothetical core-free time, **12 packets containing 12,288 payload bytes** have arrived. A 4+1 packet window holds only five 1,024-byte payloads; the sixth arrives at source-relative cycle 4,017,633, before the assumed release at cycle 4,764,083 (100 MHz clock).

These assumptions do not establish an unconditional device requirement: a different decode time, packet timing, frame size, frame drop policy, overlapping compressed-frame banks or receiver design would change the answer. A zero-decode control yields zero queued packets for this pair. The actual core additionally waits for a display boundary, and real QSPI/CPU service is not instantaneous. A real bounded system can discard busy frames rather than retain them, but the discard/abort policy must preserve any previous pending frame and recover on the next valid SOF. The calculation is not evidence that every frame will fail or that a particular final frame rate is achievable.

To run:

```sh
python3 fpga/experiments/throughput30/burst/streaming-feasibility/analyze.py \
  --fixtures /path/to/completed-network-rtl-study-build/fixtures
```

The recorded result is in `result.json`. The fixture files can be generated by `../network-rtl-study/run.sh`. No claim is made that the 5-slot window can bridge the real busy interval; implementing the packet-to-RTL replay must account for this pressure instead of silently buffering a complete JPEG or waiting indefinitely.

## Bounded queue comparison

`queue_model.py` is a separate Python discrete-event scenario using **all 267 actual clean trace arrivals**. It reconstructs each MSV1 datagram and verifies the recorded hash, feeds delivered packets through the actual Python reference reassembler, checks completed bytes, and accounts for every frame. The synthetic sink is single-frame and becomes busy at modeled commit. It uses the largest observed baseline commit-to-present time, **33.97969 ms**, as a fixed busy duration. This is conservative relative to those ten prior samples, not a verified bound on other frames, phases, firmware or hardware. Packet service is assumed at **200 µs per KiB** of payload, a deliberately simple assumed cost; CPU scheduling, CRC, QSPI control, abort and retry costs are zero. LCD phase, packet loss and retransmissions are not modeled.

The queue counts the complete 40-byte MSV1 header plus payload and includes the packet in service. It excludes socket buffers and allocator overhead. `drop-busy` immediately discards a frame if its SOF arrives while the sink is busy; subsequent packets of that frame are ignored. `buffer-busy` retains incoming packets in FIFO order while the sink is busy; on capacity overflow the entire affected frame is discarded and its queued packets are removed. Neither policy is claimed to match the production loop or the experimental Rust Window's actual busy/error semantics. The simulator's Python storage for the input event trace is separate from these modeled staging limits. Modeled "presentation" means release after the assumed fixed busy delay.

| Policy and modeled staging capacity | Modeled completed frame IDs | Dropped IDs | Max staging | Max capture-to-release age |
| --- | --- | --- | ---: | ---: |
| Drop busy, 5 × 1,064 = 5,320 bytes | 0, 2, 4, 6, 8 | 1, 3, 5, 7, 9 | 1,338 bytes | 62.94136 ms |
| Buffer busy, 32,768 bytes | 0, 1, 2, 3, 5, 6, 7, 8 | 4, 9 | 32,636 bytes | 80.23961 ms |
| Buffer busy control, 262,144 bytes | 0–9 | none | 55,859 bytes | 115.23548 ms |

These ten-frame synthetic examples illustrate the latency/drop/storage tradeoff under one particular service assumption; they do not prove 15 fps, sustainable 30 fps or a device memory requirement. In particular the largest buffer shows why a practical design also needs an explicit frame-age limit or replacement policy. All modeled drops include reason and timestamp in `queue-results.json`.

Reproduce the first two cases with `python3 queue_model.py --fixtures /path/to/fixtures`; use `--large-bytes` and `--service-us-per-kib` to vary the larger queue and service assumption. Run the three directed consistency/negative checks using `FIXTURE_DIR=/path/to/fixtures python3 test_queue_model.py`. They check bounds, frame accounting, a large-buffer aging case and fixture corruption rejection. This is not the requested packet-to-RTL bridge; that remains future work with actual sink transaction and credit semantics.

## Freshness policy experiment

The same simulator also evaluates a research-only `fresh` policy at both 5,320- and 32,768-byte limits. It does not change the baseline behavior. It drops an arriving new SOF while another frame is actively being received or its first packet is in service, preserving the active frame. While a completed frame is pending its fixed modeled presentation delay, a newer SOF replaces all older **waiting**, unstarted frames in the queue. The pending frame is not aborted. If a waiting frame reaches its capture-age deadline before its first packet begins service, the whole waiting frame is discarded. The default is **50 ms**, configurable with `--deadline-ms`; it is a deadline for beginning service, not a display deadline. A frame already being received is not canceled merely for age. Queue overflow discards the affected whole frame; if it was partially forwarded the model resets the reference receiver and never commits that partial frame. An incomplete active receive is discarded after a fixed 100 ms total from its modeled start, not an inactivity timer. Abort, reset and timeout operations consume zero simulated time. The actual hardware's abort/pending races are not represented, so this establishes no safety property for it.

| Policy and staging budget | Modeled completed IDs | Dropped IDs and reason | Max staged bytes | Max capture-to-release age |
| --- | --- | --- | ---: | ---: |
| Existing drop-busy, 5,320 B | 0, 2, 4, 6, 8 | 1, 3, 5, 7, 9: busy | 1,338 | 62.94136 ms |
| Fresh, 5,320 B | 0, 2, 4, 6, 8 | 1, 3, 5, 7, 9: overflow | 5,320 | 62.94136 ms |
| Existing buffer-busy, 32,768 B | 0, 1, 2, 3, 5, 6, 7, 8 | 4, 9: overflow | 32,636 | 80.23961 ms |
| Fresh, 32,768 B | 0, 1, 3, 4, 6, 7, 9 | 2, 8: replaced; 5: active | 28,071 | 69.15278 ms |

In this one short trace the larger fresh queue reduces the maximum modeled age by 11.08683 ms while completing one fewer frame. No frame in this trace was discarded specifically by the 50 ms start deadline; the improvement comes from replacement and protecting active work. The deadline is therefore tested separately using directed cases and is not evidence of an observed deadline-triggered gain. `queue-freshness-results.json` retains every modeled drop reason/time and completion time. `test_queue_model.py` now exercises ten checks, including output ordering, pending and active preservation, truncated-frame timeout, reordering, queue overflow, stale waiting frames, accounting and corrupted input. This remains a Python what-if model, without production, target, RTL or hardware support.
